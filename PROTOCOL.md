# LibreTag wire protocol, version 2 (LT2)

Status: 2026-11-26, firmware 0.10.0 ("0.10.0", the quiet mesh, released together with app 0.14.0, Android bridge 0.6.0, Python bridge 0.7.0 and PWA 0.5.0, with no compatibility to older versions: zero-hop report copies, the ACK, schedule anchors, scoped flood levels and direct routing, sections 2.6, 2.7, 3.3 to 3.5 and 4.3; design note `docs/design/quiet-mesh.md`; vectors `docs/vectors/quiet-mesh-v1.json`, made by `uv run python -m libretag.quietmesh vectors`, reference `host/src/libretag/quietmesh.py`. Earlier: "0.9.0": report sealing v2 with a commitment to the mailbox key, section 2, and signed mailbox entries, section 4; additions marked "0.6": quiet, `next_in`, energy, BLE and Wi-Fi packets, `BLE_SCAN`; "0.7": checks, parked quiet, commands at checks, `check_s`; "0.7.3": report every n-th wake-up, check window by radio preset, commands by flood; "0.7.6": transmit limits (2.5), low-battery report once per crossing, `dfu`, `txcap`; "0.7.7": commands over Bluetooth advertising, 3.1; "0.7.8": `selftest`, a quiet boot report inside a Wi-Fi zone). 0.7.6 and 0.7.8 add nothing to the wire format. Every 0.6 and 0.7 field sits in bytes or bits that older firmware sent as 0, so a newer decoder reads older reports and the other way round. Replaces v1 (LT1) completely; v1 is no longer supported. Reference implementation: `host/src/libretag/lt2.py`. C core: `firmware/lt_core/`. Test vectors: `host/tests/vectors/lt2.json` (generated by `uv run python -m libretag.lt2 vectors`), used by the tests in C, Python and Kotlin.

All integers are little-endian. `||` is concatenation. `HMAC` is HMAC-SHA256. `u32(n)` is 4 bytes LE, `u16(k)` 2 bytes LE, `u8(j)` 1 byte.

Why v2: resistance to a repeated `n` (SIV), separate keys for reading and for commands, a ratchet (the past is protected if the tracker is stolen), a 4 B tag for lookup on the radio and on Nostr, neighbouring repeaters in every report, a fixed length on the 16 B grid of a MeshCore channel.

## 1. Keys

At pairing the tracker generates `K0` (a 32 B random secret). The app reads it over USB while the tracker is not locked (section 6). From `K0`:

```
id      = HMAC(K0, "LT2-id")[0:8]       # public identifier for USB, reveals nothing
V_0     = HMAC(K0, "LT2-view")          # chain for reading and recognising reports
C_0     = HMAC(K0, "LT2-cmd")           # chain for commands
usb_key = HMAC(K0, "LT2-usb")           # unlocking the USB console
dm_sk   = HMAC(K0, "LT2-dm") mod n(secp256k1)   # the tracker's Nostr key for DMs to the owner
```

**Ratchet:** epoch `e(n) = floor(n / 64)`. `V_{e+1} = HMAC(V_e, "LT2-next")`, likewise `C_{e+1}`. The tracker keeps only the current `V_e`, `C_e` (plus `id`, `usb_key`, `dm_sk`) and deletes `K0` after locking. The old epoch is physically overwritten (the keys are in a raw flash page, not in LittleFS). Whoever steals the tracker and reads it out cannot read older reports. The app keeps `K0` and computes the epochs.

**Sharing:** `V_e` from a given epoch (without `C`) is enough to find and read reports from that epoch onward, but not for commands or for the past. The app shares a tag at one of three levels, always from the current epoch `e` and never with `K0`:

| Level | Link carries | The other device can |
|---|---|---|
| View | `V_e` | read reports from epoch `e` on |
| View and control | `V_e`, `C_e` | also send commands (section 3) and sign mailbox entries (4.2) |
| Full access (app 0.13.3) | `V_e`, `C_e`, `usb_key`, `id` | also unlock the USB console (6) and open the Bluetooth console and its wake advert (6.2, 3.2) |

```
libretag://share?v=1&name=<name>&type=<type>&mark=<colour>-<symbol>&e=<e>&ve=<hex V_e>[&ce=<hex C_e>[&uk=<hex usb_key>&id=<hex id>]]
```

Values are percent-encoded (a space as `%20`). `uk` (32 B) comes only together with `ce` and `id` (8 B); a link with `uk` but without either one, or with a key of the wrong length, is invalid as a whole. `id` is what a locked tracker prints (`LIBRETAG ID`), so the app knows which tag is on the cable or behind a Bluetooth advert without trying the key on every tag.

Full access gives the console key and not `K0`, because the console needs nothing else: the USB unlock (6), the Bluetooth handshake and session keys (6.2) and the wake advert (3.2) are all keyed with `usb_key`. Without `K0` the other device still cannot read reports before epoch `e` or sign as the tracker's Nostr key `dm_sk` (section 5). That limit only holds for the past: an unlocked console takes `newkey` and `unpair` on the cable, so whoever has full access can re-key the tracker and lock the owner out. The app says so before it shows the code. A device that re-keys the tracker gets the new `K0` from `status` and becomes its owner. Vectors: `host/tests/vectors/share.json` (`uv run python -m libretag.share vectors`), used by the Python and Kotlin tests.

## 2. Report (tracker → network)

Report `n` can be sent in several copies `j`. Copies 0, 1, 9, 10 and 11 carry the same report; the app merges them by `n`. Other values of `j` seal other packets that belong to report `n` (0.6):

| `j` | What | On air | Plaintext |
|---|---|---|---|
| 0 | report, flood on the home network at the tag's scope level (2.7) | yes | report (33 B) |
| 1 | report, neighbouring network near a border, or without a fix the previous network (SPEC 6.4, 0.9.6) | yes | report (33 B) |
| 2 | history record of a sent report (section 6) | never | report (33 B) |
| 3 | history record of a wake-up without a report, `n` = the next counter (several records may share it) | never | report (33 B) |
| 4 | Wi-Fi packet after report `n` (LOST) | yes | Wi-Fi (33 B), 2.4 |
| 5 + k, k = 0…3 | BLE packet k after report `n` (`BLE_SCAN`, LOST) | yes | BLE (129 B), 2.3 |
| 9 | report, zero-hop: the "hello" (0.10.0) | yes, DIRECT with an empty path | report (33 B) |
| 10 | report, flood one scope level wider than copy 0 of the same report (0.10.0, 2.7) | yes | report (33 B) |
| 11 | report, DIRECT along the tag's stored path to a bridge (0.10.0, 3.4) | yes | report (33 B) |

A copy 9 was only ever sent zero-hop, so whoever delivered it heard the tag directly. A copy 11 was only ever sent along the path, so the bridge that delivered it sits at the end of that path. At a bridge both arrive as a DIRECT packet with an empty path and look the same; only the app, which knows `j`, tells them apart.

**Sealing v2 (0.9.0), copies on air (`j` = 0, 1, 9, 10, 11).** The type byte `0x21` of the plaintext is not sent (the lookup of `x` already says it is a report). The freed space carries `c`, a 3 B commitment to the mailbox key of report `n` (section 4), and the mac is 6 B:

```
pt'   = report plaintext without byte 0                       # 32 B
kd    = HMAC(V_e(n), "LT2-r2" || u32(n) || u8(j))
k_enc = kd[0:16], k_mac = kd[16:32]
x     = HMAC(V_e(n), "LT2-x" || u32(n) || u8(j))[0:4]
mac   = HMAC(k_mac, x || pt')[0:6]
ct    = AES-128-CTR(k_enc, IV = mac || 10×0x00, pt')
sk_n  = HMAC(C_e(n), "LT2-mb" || u32(n)) mod N               # N = order of secp256k1; 0 becomes 1
pk_n  = sk_n · G, x-only (BIP-340), 32 B
c     = SHA-256("LT2-mbc" || pk_n || x || ct || mac)[0:3]
P     = x || c || ct || mac                                   # 4 + 3 + 32 + 6 = 45 B
```

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | `x` |
| 4 | 3 | `c` (not under the mac: it is computed from it) |
| 7 | 32 | `ct`: plaintext bytes 1…32 |
| 39 | 6 | `mac` |

A report forged without `V_e(n)` passes the mac with chance 2⁻⁴⁸ per attempt. SIV still holds: the key is per `(n, j)`, so the IV only has to differ for different content under that one key. `c` is for bridges only (section 4): `sk_n` needs the command chain `C_e(n)`, so only the owner and a control share can sign for report `n`. The tracker computes one public key per sealed copy (`lt_mailbox_sk` and `lt_secp_pubkey`; `selftest` prints the time as `pk_us`), so a tracker build needs `CONFIG_LIBRETAG_NOSTR` (libsecp256k1). Vectors: `reports` (with `pk`), `mailbox_keys` in `lt2.json`.

**Plain seal, every other packet (`j` = 2 to 8) and commands.** History records (`j` = 2, 3, never on air), the Wi-Fi packet (`j` = 4) and the BLE packets keep the type byte and an 8 B mac:

```
kd    = HMAC(V_e(n), "LT2-r" || u32(n) || u8(j))
k_enc = kd[0:16], k_mac = kd[16:32]
mac   = HMAC(k_mac, x || pt)[0:8]
ct    = AES-128-CTR(k_enc, IV = mac || 8×0x00, pt)
P     = x || ct || mac
```

There is no other report sealing: firmware before 0.9.0 sealed copies 0 and 1 with the plain seal, and current apps and bridges do not read that (vectors `history` pin the plain seal of a report plaintext).

This is SIV: the IV is derived from the content. The same `(n, j)` with the same content gives the same bytes (repeated transmissions and copies from bridges merge), and with different content a different IV, so nothing is revealed even if the counter goes wrong.

**Opening:** `x` in the table `x → (n, j)` (window `last_n − 256 … last_n + 2048`, `j ∈ {0, 1, 9, 10, 11}`, five tags per counter) → keys → decrypt with the IV from `mac` → recompute `mac` (constant-time comparison); for the copies on air with the v2 keys and the 6 B mac, putting the type byte `0x21` back in front. BLE and Wi-Fi packets (`j` 4…8) follow their report within seconds, so a second, small table covers only `n ∈ last_n − 8 … last_n + 64` (`ReportWindow.open_extra` / `tryOpenExtra`). The length of `P` tells the kind: 45/51 B report or Wi-Fi, 141/147 B BLE.

### Report plaintext (33 B)

| Offset | Type | Field |
|---|---|---|
| 0 | u8 | type `0x21` (LT2 report; not on air since 0.9.0, see sealing v2 above) |
| 1 | u8 | `flags`: bit 0 `HAS_FIX` (the position is from this wake-up), bit 1 `CMD_ACK`, bit 2 `LOW_BATT`, bit 3 `NB_DISCOVER`, bit 4 `QUIET` (0.6, 2.1), bit 5 `QUIET_OWNER` (with `QUIET`: the reason is the owner's device nearby, else a home zone), bit 6 `BLE_SUM` (bytes 28–30 hold a BLE summary), bit 7 `SYNC` (0.10.0: the tag's schedule anchor is report `n − 1`, 2.6; 0.7 to 0.9 used the bit as `CHECKS`, now every tag listens at its slots) |
| 2 | u8 | bits 0–1 `mode` (0 IDLE, 1 TRACK, 2 LISTEN, 3 LOST; bits 0–2 before 0.9.4, where bit 2 was always 0), bit 2 `BOOT` (0.9.4: the first report since the tracker booted, see below), bit 3 `PARKED` (0.7: with `QUIET` and without `QUIET_OWNER` the reason is parked, else a home zone), bits 4–7 `cmd_seq & 0x0F` of the last executed command |
| 3 | u8 | battery % (255 = unknown) |
| 4 | u32 | fix time (Unix s, from GPS); without `HAS_FIX` the time of the **last** fix; 0 = no fix yet |
| 8 | i24 | latitude: `round(lat · 2²³ / 90)` (~1.2 m) |
| 11 | i24 | longitude: `round(lon · 2²³ / 180)` (~1.6 m at 48°) |
| 14 | u8 | horizontal accuracy in m (255 = unknown); in a `BOOT` report without `HAS_FIX` the reset information instead (0.9.4, below) |
| 15 | u8 | bits 0–3 total repeaters (max 15), bits 4–6 number of entries below (0–5), bit 7 `WIFI` layout of bytes 16–30 (2.2) |
| 16 | 5 × 3 B | repeater: first 2 B of the public key, SNR × 4 (i8, dB). With `BLE_SUM` at most 4 entries and bytes 28–30 are: u8 BLE devices seen, u8 of them with a stable address (public or random static), i8 RSSI of the strongest stable one (0 = none) |
| 31 | u8 | `next_in` (0.6): when the tracker will next be heard. 0 = not stated; 1…120 = v × 30 s; 121…255 = 1 h + (v − 120) × 15 min (to 34.75 h). Counted from this transmission to the start of the wake-up that transmits; the report itself follows after the fix search. With `QUIET` it is the heartbeat (24 h zone, 8 h owner, 24 h parked by default). 0.10.0: it is the time until the tag next transmits something the receiver of this copy should get: in a zero-hop or routed copy the next hello, in a flood copy the next flood the tag already knows about (the next report while moving, the heartbeat when quiet, the backoff gap without a fix, the time the IDLE flood budget frees) |
| 32 | u8 | energy (0.6): charge used since the last full charge, estimated by the tracker from its on-times; 0 = not counted, else `1 + mAh / 10` (255 = 2540 mAh or more). The count restarts when the battery reads ≥ 4.15 V (charging) |

- Repeaters are in every report (also with a fix: the place fingerprints are learned from them, SPEC 6.5). `NB_DISCOVER`: replies to a zero-hop `CTL_TYPE_NODE_DISCOVER_REQ`, where SNR is the one with which the repeater heard the **tracker**. Otherwise they are repeaters heard directly (the last hop of the flood), with the SNR with which the tracker heard them. Sorted from the strongest. The tracker sends the discover alongside the GPS search when its previous wake-up had no fix and its link is FAR or ROUTED (0.10.0; a NEAR tag sends one only for the moved-without-GPS test, SPEC 3.2). In LOST it also sends one after a search that ended without a fix, if none went out in that wake-up (0.7.1). A quiet tracker sends none.
- Position age = receive time − fix time; the tracker does not need a clock.
- **Boot report (0.9.4).** The first report the tracker transmits after a boot has `BOOT` (byte 2 bit 2), and so has its history record (`j = 2`). A wake-up that only writes a silent record (`j = 3`) does not use it up: the bit goes with the next transmitted report. When that report has no `HAS_FIX` and is not in the Wi-Fi seed2 layout (2.2: Wi-Fi layout without any fix time, where byte 14 is the second BSSID's RSSI), byte 14 carries the reset information instead of the last fix's accuracy: bits 0–2 the cause, bits 3–7 the resets in a row at boot (`boot_resets`, capped at 31). With a fix, or in the seed2 layout, byte 14 keeps its meaning and only the bit is set. Cause codes are the words `status` prints as `last_reset=` (6.1): 0 `none` (no flag: the nRF52 reports power-on and brown-out alike that way), 1 `pin`, 2 `power`, 3 `soft`, 4 `debug`, 5 `brownout`, 6 `watchdog`, 7 `crash`. The firmware maps its `LT_RST_*` bits to one code in the same order as `last_reset=`: crash, watchdog, brown-out, then pin, debug, power, soft (`lt_boot_cause`, `lt_boot_info`). The app shows the position of a boot report without a fix with no accuracy. The bit is inside the sealed plaintext, so nothing changes on air. A decoder from before 0.9.4 reads the mode with mask `0x07` and sees mode 4 to 7 in a boot report (the reference falls back to IDLE). Vectors `boot_reports` in `lt2.json`.

### 2.1 Quiet (0.6) and checks (0.7)

**0.10.0:** quiet in a home zone or parked means **no flood**. The tag still sends its hello (copy 9) at every reporting wake-up, with `QUIET` and its reason, and floods only by the rules of SPEC 3.2 (the heartbeat is a flood only for a FAR or ROUTED tag, every 24 h). Quiet because of the owner stays fully silent between its heartbeats. Parked starts at the second report within `MOVE_M` (300 m, or 3 × the accuracy) of the first, with a 24 h heartbeat (`still 2 24`). The text below describes the wake decision, which is unchanged apart from those values.

Quiet means no report: the tracker wakes up, takes a fix, decides, and goes back to sleep without transmitting. Only the last report before a quiet stretch carries `QUIET` (with the reason: `QUIET_OWNER` for the owner, `PARKED` for parked, neither for a home zone), with `next_in` = the heartbeat; the app then waits for that report instead of raising "not responding" after 3 intervals.

The decision is one pure function, `lt_wake_decide` (`firmware/lt_core`), mirrored in `host/src/libretag/wake.py`; the vectors `wake` in `lt2.json` pin both (with the default settings in `wake.cfg`; a scenario with its own `cfg` overrides them), and `host/tests/test_wake.py` runs multi-day scenarios through the simulator (`sim.simulate_days`). At each wake-up, in this order:

1. Mode TRACK, LOST or LISTEN, or no reason below: **report** (normal). If the tracker was quiet, the stretch ends: `home_silent` goes back to "unknown" (the first report near a border goes to both networks), and if the stretch lasted 12 h or more, `n` jumps to the start of the next ratchet epoch (whoever reads the current key later cannot read back across the stretch; the app's 2048-ahead window absorbs the jump).
2. Reason **zone**: a fix inside a home zone (inside at `d < r`, still inside until `d > r + 50 m`). No fix is never a zone (fail-open: a jammer, a Faraday bag and a garage look the same). A tracker that scans Wi-Fi also has Wi-Fi zones: without a fix, a scan whose similarity to a zone's fingerprint is at least 40 (and at least 2 APs in common) is inside, and it stays inside while the similarity is at least 30 (`lt_wzone_match`, docs/design/fw-wifi-esp32.md). A scan that sees no usable AP is never a zone. A fix decides over Wi-Fi. Without a fix, parked (4. below) compares each scan with the first scan of the stretch instead of the 100 m radius.
3. Reason **owner**: one of the owner's Bluetooth anchors seen during this wake-up (works without a fix).
4. Reason **parked** (0.7): `still_after` IDLE wake-ups in a row (default 3) each had a fix within 100 m of the first of them. At hourly wake-ups the tracker goes quiet 2–3 h after it stopped. A fix outside the 100 m ends the stretch (a report at that wake-up, and the count starts again from that fix); a wake-up without a fix, or in another mode, resets the count, so no fix means a report (fail-open, as with zones). `still_after = 0` turns it off.
5. With a reason (zone wins over owner, owner over parked): the first wake-up of a stretch, or a change of reason, sends a report with `QUIET`. After that the tracker is silent until the heartbeat after its last report: 24 h zone, 8 h owner (the cap for a phone stolen with the car), 6 h parked; then it sends another `QUIET` report. A report forced from the console during quiet also carries `QUIET`.

Leaving a zone or a parking place, or the owner's phone going away, is reported at the next regular wake-up (no extra reports). The IDLE interval does not slow down while the tracker stands still (0.5 doubled it; 0.7 removed that, because checks need a fixed base). The Bluetooth scan for anchors runs alongside the GPS search and never extends it. With `anchor gps on` (default) the fix is still taken while the owner is near and kept in the history as a `j = 3` record; `anchor gps off` stops the GPS as soon as an anchor answers.

**Checks.** Every IDLE wake-up without a report is a **check** (a listening slot): the tracker listens for a command for a few seconds and transmits only if a command came. Since 0.10.0 the checks run on the grid of the schedule anchor (2.6), not on the last report: slot `k` of anchor `n_a` is at `t_k = t0 + Σ (base + jit_i)` with the jitter from the slot key `ks` (2.6, vectors `slots` in `quiet-mesh-v1.json`). The 0.7 derivation from `C_e(n)` and the vectors `checks` in `lt2.json` are obsolete. The jitter stays within ±10 %, so an observer still cannot read a period, but the app has the key and computes the same times. Outside quiet IDLE (normal reporting, TRACK, LOST) the interval keeps a random jitter and every wake-up reports anyway.

**Window.** At check `k` the receiver is on from `t_k − g_k` to `t_k + check_s + g_k`, where `g_k = 2 s + (t_k − t0) × 100 ppm` (clock drift; 24 h → 10.6 s; `lt_check_guard_ms`) and `check_s` is the listening time, 30 s by default since 0.7.3 (0–180; 0 = no listening, the tracker still wakes at `t_k`; 0.7.2 had 60 s, 0.7.0 and 0.7.1 took 0–60 with 20 by default). The receiver runs alongside the GPS search and the Bluetooth scan, and if they last longer than the window it stays on until they end and still takes a command (0.7.2), so a command that crosses many repeaters still gets in while the tracker looks for a fix.

**Window by preset (0.7.3).** `check_s` is meant for SF7 / BW 62.5 kHz / CR 4/5 (Slovakia, Hungary, Czechia, the Netherlands). On a slower preset a flood takes longer per hop, but less than the airtime alone suggests: on SF8 / CR 4/8 networks (Germany, Poland, Saarland) the measured delay per hop was ×1.5–1.7 at the median and about ×2.0 at p90 against SF7 / CR 4/5 (median 1.0 s per hop), while the airtime is ×2.7 (`docs/research/flood-latency.md`, "Slower presets"). So the tracker listens `check_s × (0.4 + 0.6 r)`, rounded up, where `r = A(preset) / A(SF7/62.5/CR5)` and `A` is the LoRa time on air of a 35 B command packet (explicit header, CRC, preamble 16); never less than `check_s`, at most 180 s (`lt_check_window_s`, `wake.check_window_s`, vectors `check_window`; 0.7.4, 0.7.3 used `r` alone). 30 s becomes 59 s on SF8 / CR 4/8 (EU/UK Narrow, Switzerland), 42 s on SF9 / 125 kHz, 67 s on SF11 / 250 kHz. The preset is the one the tracker listens on (its home network). Senders do not need to know: they transmit at `t_k + 1 s` (0.10.0; `t_k + 3 s` before).

**Report every n-th wake-up (0.7.3).** With `report_every = R` (1–24, default 3 since 0.10.0; console `report every <n>`, `SET_IDLE` byte 8) the tracker in IDLE still wakes every `interval`, but after report `n` its wake-ups follow the keyed schedule above also outside quiet, and only wake-ups `k` with `k mod R = 0` look (GPS, Bluetooth scan) and decide (`lt_wake_reports`). The others only open the check window: no GPS, no transmission, and since 0.9.3 only a 1.5 s Bluetooth scan for the owner's command advert (3.1), alongside the window. A command there (sealed for slot `k` of the anchor, 2.6) is answered by the rule of 3.5. A normal report's `next_in` is then `t_R − t0` (`lt_check_offset(C_e(n), n, R, base)`), so the app knows the next report and the checks before it. While quiet the same rule holds: wake-ups that do not look only listen, so leaving a zone or a parking spot is noticed at the next wake-up that looks; the heartbeat is unchanged. The app knows `R` from its own settings (or the backup's `report_every`). With `check_s = 0` the wake-ups that would only listen are skipped. Vectors `report_every`. The wake decision waits until both the window and the search are over, or a command arrives, so a report caused by a change goes out at most `max(check_s + 2 g_k, search)` after the wake-up. Senders transmit at `t_k + 1 s`. The app takes `t0` from the anchor report's receive time (`created_at` of its event, or the own node's receive time); flood latency of a few seconds is inside the guard. The tracker's clock runs on its 32.768 kHz crystal (±20–50 ppm), at most half of the allowance.

The app knows `interval_min` because it set it (over USB or with `SET_IDLE`). With an interval the app does not know it shows only the heartbeat. Changing the interval over USB during quiet makes the next wake-up a report, so the schedule restarts on the new interval.

### 2.2 Wi-Fi layout of the report (0.6, `WIFI` = byte 15 bit 7)

For trackers with a Wi-Fi scanner (docs/design/wifi-positioning.md). The Heltec ESP32-S3 boards scan with their own radio (`CONFIG_LIBRETAG_WIFI`, `lt_wifi_scan()` in `lt_wifi_esp32.c`, docs/design/fw-wifi-esp32.md); other boards have only the hook. The selection is `lt_wifi_select`. Bytes 16–30:

| Offset | Size | Field |
|---|---|---|
| 16 | 3 B | at most 1 repeater (entries in byte 15 bits 4–6), or a second tail (below) |
| 19 | 6 B | seed: a full BSSID, as written (`aa:bb:…`, first byte first), the strongest globally administered one |
| 25 | u8 | bits 0–4 RSSI q (dBm = −95 + 2q), bits 5–7 APs in the scan (7 = 7 or more) |
| 26 | 3 B | tail: last 3 bytes of another BSSID; rotates over the next 7 best with `n` (with a second tail: `2n`, see below) |
| 29 | u8 | bits 0–4 RSSI q, bit 7 tail present |
| 30 | u8 | 0, or with a second tail: bits 0–4 its RSSI q, bit 7 set |

**Second tail in the repeater's slot.** When the scan gives at least two tail candidates (the usable APs after the seed and, below, the second seed: so at least 3 usable APs, 4 with a second seed), bytes 16–18 carry a second tail instead of the repeater, byte 30 its RSSI q with bit 7 set, and byte 15 bits 4–6 say 0 entries (bits 0–3 still count the repeaters heard). The two tails take turns over the same list of the next 7 best: tail `rest[2n mod k]`, second tail `rest[(2n + 1) mod k]`, so the app still collects all of them over a few reports. A decoder reads bytes 16–18 as a tail when `WIFI` is set and byte 30 bit 7 is set. An older decoder sees no repeater entry and ignores byte 30, which older firmware always sent as 0. With fewer candidates the layout is the one above (one tail, the repeater stays). Vectors `wifi`, `wifi_nofix` (two tails) and `wifi_few` (one tail and the repeater).

`BLE_SUM` is not used together with this layout. SSIDs ending in `_nomap` or containing `_optout` are never sent; locally administered MACs (hotspots) are never a seed. The app asks a position service for the seed and matches the tails against the neighbours it returns.

**Second seed without a fix time.** A tracker that never had a fix (fix time 0, e.g. an ESP32 board without GPS, `docs/design/fw-wifi-esp32.md`) has nothing to say in bytes 8–14. With the `WIFI` layout and fix time 0 they carry a second full BSSID: bytes 8–13 the BSSID as written (the second-strongest globally administered one), byte 14 bits 0–4 its RSSI q, bit 7 set. The tail then rotates over the APs after both seeds. A decoder takes bytes 8–13 as a BSSID when `WIFI` is set, the fix time is 0 and the bytes are not all zero; older decoders ignore them, because with fix time 0 there is no position. Two full BSSIDs per report are what BeaconDB needs at minimum.

### 2.3 BLE packet (0.6, type `0x23`, `j = 5 + k`)

After a `BLE_SCAN` command, and in LOST after every `lostble`-th report, the tracker sends what Bluetooth heard as up to 4 packets, sealed like report `n` copy `j = 5 + k`. Plaintext 129 B (`P` 141 B, channel datagram 3 + 144 = 147 B; stealth: 135 B plaintext with 6 zero bytes, `P` 147 B). Every packet is readable alone.

| Offset | Size | Field |
|---|---|---|
| 0 | u8 | type `0x23` |
| 1 | u8 | bits 0–1 k, bits 2–3 packets − 1, bit 4 active scan, bit 5 truncated (devices left out) |
| 2 | u8 | scan seconds |
| 3 | u8 | devices seen |
| 4 | u8 | of them with a stable address (public or random static) |
| 5 | u8 | with a rotating address (RPA, NRPA) |
| 6 | u8 | rotating with Apple maker data (`0x004C`) |
| 7 | u8 | rotating with Microsoft maker data (`0x0006`) |
| 8 | … | records until a length byte 0 or the end |

Record: `u8 len` (bytes that follow), address 6 B as written, `u8 info` (bits 0–1 kind: 0 public, 1 random static, 2 RPA, 3 NRPA; bit 2 connectable, bit 3 a scan response was seen, bit 4 one of the owner's anchors), `i8` strongest RSSI, `u8` adverts heard, then AD structures exactly as on air (`len`, `type`, data): complete or shortened name (full string), manufacturer data (company id + data), 16-bit service data, appearance, 16-bit UUIDs, TX power, the first 128-bit UUID. Order of records: the owner's devices, stable addresses, named rotating ones, the rest; louder first. A record never spans two packets; when a record does not fit, trailing AD structures are dropped only in the last packet.

The next report after a `BLE_SCAN` (in LOST the same report) carries the summary in bytes 28–30 (`BLE_SUM`).

### 2.4 Wi-Fi packet (0.6, type `0x24`, `j = 4`)

33 B like a report: type `0x24`, u8 APs in the scan, a second seed BSSID (6 B), its RSSI q, then 6 × (3 B tail + u8 meta: bits 0–4 q, bit 7 present). Sent in LOST after the report, by boards with a Wi-Fi scanner.

### 2.5 Transmit limits (0.7.6)

These change when the tracker transmits, not what it sends. Details and constants: `docs/design/fw-0.7.6.md` 2 and 3, `lt_core` (`lt_txcap_*`, `lt_base_interval_s`, `lt_lost_interval_s`), Python mirror `host/src/libretag/policy.py`.

- TRACK and LOST report at most every 120 s (`LT_TRACK_MIN_S`). A `SET_MODE` interval, the console `track` and a saved mode resumed at boot are raised to 120 s.
- At most 200 floods in a rolling 24 h (`LT_FLOOD_CAP_24H`, 24 hourly buckets in RAM, a reboot starts from zero). Every flooded packet counts: copies 0, 1 and 10, BLE and Wi-Fi packets sent as floods, DMs. Zero-hop and routed copies, ACKs and the discover do not. The retransmission of the same bytes 8 s after a report is gone (0.10.0): copy 10 replaces it. Over the cap the next interval in every mode is `max(IDLE interval, 1 h)` and `next_in` says so. In IDLE on the keyed schedule a wake-up that would report only listens, and the heartbeat still reports. The answer to a command (report `n + 1` with `CMD_ACK`, `BLE_SCAN` packets), console `report`/`test` and the low-battery report still go out.
- **IDLE fallback floods (0.10.0):** at most 8 in a rolling 24 h (events and command answers excluded). Over it the tag sends hellos only, and `next_in` of the last flood says when the budget frees. Unscoped floods in IDLE at most once in 24 h (2.7).
- LOST doubles its interval after 2 h while each fix stays within 100 m of the first fix of that stretch. A fix outside sets a new reference and the interval drops back at once. An app should use `next_in` in LOST instead of assuming 10 min.
- No transmission below 3250 mV (again from 3350 mV or on USB). The first report after a boot comes after 30 s, after resets in a row after 2, 4, 8 … min, at most 1 h. Resets in a row count only boots the owner did not cause (firmware 0.9.1): brown-out, watchdog, crash, an unannounced software reset. Reset button, power-on, the USB-serial chip's reset, `reboot` and `dfu` set the count to 1.

### Transport

**Channel `#libretag`** (default): a MeshCore channel with key `SHA-256("#libretag")[0:16]`, `data_type 0xFF4C`, datagram content = `P` (45 B). The MeshCore plaintext `data_type || len || P` is 48 B (without padding), the `GRP_DATA` payload 1 + 2 + 48 = 51 B. Header `0x19` (flood), with a region `0x18` + 4 B transport codes (2.7), `path_len` with the network's hash size (SPEC 6.4).

**Route of each copy (0.10.0).** Copy 9: header `0x1A` (DIRECT), `path_len` = hash size bits with count 0, no transport codes. Copy 11: header `0x1A` with the stored path in send order (tag to bridge). Copies 0 and 1: floods as above at the tag's level. Copy 10: like copy 0, one level wider. ACKs and commands: 3.3, 3.4. A command's fallback send uses `data_type 0xFF6C`. A receiver tells the payload by the datagram length: 45 B report or Wi-Fi packet, 141 B BLE packet, 29 B command, 13 B near ACK, 15 to 20 B routed ACK. Vectors `copies` in `quiet-mesh-v1.json` (packet bytes for every copy).

**Stealth** (optional): `GRP_DATA` without the channel envelope, plaintext 39 B (33 B + 6 zero bytes; with sealing v2 `pt'` is 32 + 6 = 38 B and `c` covers all of `P` but bytes 4…6), `P` 51 B, so the same shape as a normal MeshCore channel packet (1 + 2 + 48). The first byte (`x[0]`) serves as the "channel hash".

BLE packets (2.3) use the same two transports: on the channel `P` is 141 B and the `GRP_DATA` payload 1 + 2 + 144 = 147 B; in stealth `P` is 147 B. The Python bridge (`nostrmesh`) publishes 141 B datagrams as kind 4243 like reports (0.6).

### 2.6 Schedule anchor and listening slots (0.10.0)

Commands and late ACKs reach an IDLE tag at its listening slots ("checks"). A sender has to know when the tag listens and what to seal for that moment. Both come from the tag's **schedule anchor** `n_a`, a report the app is known to have. A hello that nobody confirmed does not change the schedule. Reference: `host/src/libretag/quietmesh.py` (`slot_key`, `slot_offsets`, `TagSchedule`, `AppAnchor`). Vectors: `slots`, `tag_schedule`, `app_anchor` in `docs/vectors/quiet-mesh-v1.json`.

**When the anchor moves.** Only in two cases:

1. A flood copy (`j` = 0, 1 or 10) of report `n` goes out. The anchor becomes `n`, with `t0` = the transmission of the first flood copy of `n`. Copy 10 or copy 1 of the same report does not move it again.
2. An ACK for `(n, 0)` arrives in the listen window of report `n` (3.3). If the anchor is not `n` yet (a hello or a routed copy), it becomes `n` with `t0` = the first transmission of `n`. If a flood of `n` already moved it, the anchor stays as the flood set it.

An ACK at a slot, a hello without an ACK, and a command change nothing. After a reboot there is no anchor until the boot report goes out (the time base is the uptime). TRACK and LOST have no slots (each report has its own listen window), but the anchor rules still run, so the grid is right when the tag returns to IDLE.

**The previous grid.** When a flood moved the anchor, the tag keeps listening at the next 3 slots of the previous grid and takes commands sealed for it, because a flood is never confirmed and the app may have missed it. When an ACK moved the anchor, the previous grid is dropped at once: the app made that ACK, so it has the report.

**Slot key.** At the moment the anchor moves the tag derives

```
ks = HMAC(C_e(n_a), "LT2-slot" || u32(n_a))
```

and keeps it until the next anchor (and, for 3 slots, the previous grid's `ks`), so the grid survives the ratchet moving on.

**Slot times.** Slot `k = 1, 2, …` of the grid lies at

```
t_k   = t0 + Σ_{i=1..k} (base + jit_i)
base  = interval_min × 60                     (the IDLE interval)
span  = floor(base / 5)
jit_i = (u16_le(HMAC(ks, "LT2-w" || u16(i))[0:2]) mod span) − floor(span / 2)      (span 0 → 0)
```

The jitter comes from `ks`, not from `C_e(n)` as in 0.7, so the tag needs no older epoch key. Wake-ups `k` with `k mod report_every = 0` look (GPS, Bluetooth) and may report; the others only listen.

**Window.** At slot `k` the receiver is on from `t_k − g_k − e` to `t_k + W + g_k`. `g_k = 2 s + (t_k − t0) × 100 ppm`. `W` is the check window of 2.1 (30 s on SF7, scaled by preset). `e` is 0, except for a grid set by a flood that followed a hello or a routed copy of the same report in the same wake-up: then `e` is the wait between the first copy and the flood, rounded up to whole seconds (12 s after a hello, 13 or 14 s after a routed copy). A sender that only had the first copy counts from it and still lands in the window, and a bridge that only had the flood counts from the flood.

**Senders** transmit at `t_k + 1 s` (`at` of a timed entry), never earlier. The fallback flood of 3.4 leaves 12 s later, inside the window.

**What a slot accepts.** At slot `k` of the grid of `n_a`: a command sealed for `(n_a, k)` from `ks` (section 3), under either channel data type, and an ACK `Pa(n, k)` for the tag's last report `n` with that same slot number (3.3). In the listen window right after report `n`: a command for `(n, 0)` and an ACK `Pa(n, 0)`. There is one slot numbering, the anchor's.

**`SYNC`.** Flags bit 7 of report `n` is set when the anchor, at the moment report `n` is built, is report `n − 1`. The app keeps one confirmed grid `A` and at most two candidates (three grids at most), and settles them with it:

| Report `n` | The app does |
|---|---|
| a flood copy | `A = n` (its time), candidates dropped |
| has `SYNC` | `A` = the grid of `n − 1`; if the app never had `n − 1`, the schedule is unknown |
| no `SYNC`, `n = m + 1` (`m` the newest report the app had) | drops candidate `m`; `A` stays |
| no `SYNC`, `n = m + 2` | keeps `A` and candidate `m` (the missing report did not become the anchor; `m` may have) |
| no `SYNC`, `n > m + 2` | keeps its grids for sending; the schedule counts as known only if the tag stands where it stood (a fix within `MOVE_M`, no `BOOT`) and no heartbeat or `hold` flood fell due in the gap |
| a hello or routed copy the app sent a live ACK for | `n` becomes a candidate; a third candidate is not added and the schedule is unknown |
| older than `m` | history only |

A confirmed command also settles the grids: the send it answered was on the tag's grid. While the schedule is unknown the app shows no time ("schedule not known") and still sends on the grids it has.

**Sends over several grids.** A command for a NEAR or ROUTED tag is published for every grid the app holds. Only the latest of the slots keeps the flood fallback; the others carry `["fb", "0"]`, so a miss on the wrong grid causes no flood. Lost and Track keep the fallback on every slot.

### 2.7 Flood scope: bridge areas and the ladder (0.10.0)

A flood is scoped as narrowly as the tag can justify. Levels, narrow to wide:

| Level | Scope | When |
|---|---|---|
| L1 | the scope of a bridge area | the tag's last fix (any age) is inside an area row whose network is the tag's home network |
| L2 | the country's region (`sk` in Slovakia) | the country row has one, and the tag is not near a border with a neighbour on the same radio that has another region or none |
| L3 | unscoped | always; in IDLE at most once in 24 h, otherwise the widest scoped level is used |

**Areas.** A row is a centre, a radius in km, a scope name and the network (country row and radio preset) it belongs to. The firmware has baked rows (0.10.0: one, the first bridge's area, 25 km) and four rows in the state file, set by the console (6.1) or by `SET_AREA` (section 3). State-file rows are tried first. Distance is the great-circle distance; the vectors keep their points at least 1 km from any edge. Vectors `areas` use synthetic rows.

**Ladder.** The tag keeps `lvl`, the level of its next flood, starting at the narrowest available one. After flood copy 0 at `lvl`, evidence that the level works is an ACK, a command, or hearing a repeater repeat the packet. Without evidence within 8 s:

- a flood that matters (moved, `hold` ran out, heartbeat, boot, command answer, low battery, every TRACK and LOST report) sends **copy 10** one level wider, once, in the same wake-up;
- a repeated flood of a tag without a fix (the 3, 6, 12, 24 h backoff) sends nothing more;
- either way the next flood starts one level wider.

`lvl` returns to the narrowest level after an ACK, when the tag enters or leaves an area, and 24 h after it widened. Copy 1 (the neighbour or previous network) goes out only together with a flood copy 0. Each step of the ladder is another copy, because a repeater that dropped one payload for a scope it does not carry also drops the same payload in a wider scope.

**Transport code.** `key = SHA-256("#" + name)[0:16]` (a name that starts with `#` is not prefixed twice); `code[0] = HMAC-SHA256(key, payload_type || payload)[0:2]` as a little-endian u16, 0 becomes 1 and 0xFFFF becomes 0xFFFE; `code[1] = 0`. Vectors `transport`.

## 3. Command (app → tracker)

A command answers report `n` in its listen window (`k = 0`; `listen`, 60 s) or slot `k ≥ 1` of the tag's schedule anchor `n_a` (2.6).

```
kd    = HMAC(C_e(n), "LT2-c" || u32(n))
k_enc = kd[0:16], k_mac = kd[16:32]
xc    = HMAC(C_e(n), "LT2-cx" || u32(n))[0:4]
mac   = HMAC(k_mac, xc || pt)[0:8]
ct    = AES-128-CTR(k_enc, IV = mac || 8×0x00, pt)
Pc    = xc || ct || mac          # 29 B
```

In the `#libretag` channel: datagram 29 B → MeshCore plaintext 32 B → payload 35 B. As direct (along the reversed path of the report), zero-hop or flood (LOST only), see SPEC 6.2.

**At a slot (0.10.0).** A command for slot `k ≥ 1` of anchor `n_a` is derived from the slot key `ks` (2.6):

```
kd = HMAC(ks, "LT2-c"  || u16(k))
xc = HMAC(ks, "LT2-cx" || u16(k))[0:4]
```

`k = 0`, the window right after a report, keeps the derivation above with `C_e(n)` of that report. The plaintext (17 B), `Pc` (29 B) and the `cmd_seq` rules are the same. At each slot the tracker computes `xc` for its own `(n_a, k)` (and for the previous grid while it is kept) and ignores everything else, so a command for a slot that has passed cannot be replayed at a later one. Vectors: `slots.commands` in `quiet-mesh-v1.json`. The 0.7 derivation from `C_e(n) || u32(n) || u16(k)` is gone; `check_commands` in `lt2.json` is obsolete. The channel data type is `0xFF4C` for the first send and `0xFF6C` for a fallback send (3.4); the tag accepts both.

After executing a command at a slot or in a listen window, the tracker sends its answer, report `n + 1` with `CMD_ACK` (and `QUIET` if the stretch goes on), at the time 3.5 gives. A mode change (TRACK, LOST) ends the quiet stretch as before. `BLE_SCAN` runs in the window after report `n + 1`, and its packets are copies `j = 5…` of `n + 1`.

Route (0.10.0): the cheapest way from where the sender heard the tag, 3.4 and 4.3: zero-hop for a report heard directly, along the reversed path for one heard over 1 or 2 repeaters, else a flood in the report's scope; after a send along a path (and after a zero-hop send with `both`) a fallback flood with data type `0xFF6C` when no answer comes within 12 s. The sender transmits at `t_k + 1 s`: the app over MeshCore Open's Local API if it runs then, bridges from the mailbox (`at`, section 4). A check that the command misses is not the end: the next check has its own entry, and the plain entries wait for the next reports.

### Command plaintext (17 B)

| Offset | Type | Field |
|---|---|---|
| 0 | u8 | type `0x22` (LT2 command) |
| 1 | u8 | `cmd_seq` |
| 2 | u8 | opcode |
| 3..16 | | arguments (unused = 0) |

| Opcode | Name | Arguments |
|---|---|---|
| `0x01` | `SET_MODE` | u8 mode, u16 interval_s, u16 duration_min (0 = default). Since 0.7.6 the tracker raises a TRACK or LOST interval below 120 s to 120 s (2.5) |
| `0x03` | `SET_IDLE` | u16 interval_min, u16 listen_s, u8 check_s (0.7, offset 7: 1…180 s; `0xFF` = no listening at checks), u8 report_every (0.7.3, offset 8: 1…24, from the next report on), u8 ack_patience (0.10.0, offset 9: 1 = an IDLE tag that moved waits for the next check before it floods, the default; 2 = it decides 12 s after the hello, "report at once when it moves"). 0 keeps a value. With offset 9 set the command has no Bluetooth form |
| `0x04` | `BUZZ` | u8 seconds |
| `0x05` | `BLE_SCAN` (0.6) | u8 seconds (0 = 8, max 20), u8 options (bit 0 active scan: names in scan responses, but the tracker becomes visible), u8 packets (0 = 2, max 4) |
| `0x06` | `BLE_CONSOLE` (0.9.2) | u8 window in units of 10 s (0 = 180 s; the tracker clamps to 30…600 s). Opens the console over Bluetooth (6.2) at the wake-up that takes the command |
| `0x07` | `SET_AREA` (0.10.0) | u8 slot (0…3; bit 7 set = delete that row), i24 lat, i24 lon (the report encoding), u8 radius km, 6 B scope name, zero padded. A row of the state-file area table (2.7). The tag refuses a slot above 3, and for a row that is not deleted a radius of 0 or a scope name that is not 1 to 6 of `a-z 0-9 - _` followed only by zero bytes; the app refuses to build the same. Non-zero bytes after offset 8, so no Bluetooth form |

`BLE_CONSOLE` opens the Bluetooth console window at once, as after a boot (6.2): only on a locked tracker above the transmit floor; `blecon boot off` and the resets in a row do not apply (the owner asked); after 5 failed handshakes since boot it stays closed. It is acknowledged like every command (`CMD_ACK` in report `n + 1`): the report also tells bridges to drop the remaining timed entries, so it is worth its airtime. Its arguments end before offset 8, so it has a Bluetooth advert form (3.1). **Routes (app 0.11.2):** the command is for a tag next to the owner, so the app never floods it from its own radio. It goes, in this order, by the phone's command advert (3.1) when the tag's next listening wake-up also scans Bluetooth (firmware 0.9.3: every wake-up does; before, only one with known devices that is not listen-only, 2.1) and the phone is near the tag (app 0.11.3: the tag has known devices, or its last report was quiet because of one), by the owner's node zero-hop when the Local API server offers `tx_path_data` (`"path": ""`; our MeshCore Open fork offers it, and an upstream pull request carries it; a server without it is skipped, never turned into a flood), and only when neither reaches the next listening wake-up, through the mailbox (4), where bridges zero-hop or flood as for any entry. A command sent only by a local way that is still not acknowledged in a report received more than 60 s after the wake-up it was meant for goes to the mailbox from that report on (app 0.11.3). **Firmware 0.9.5, app 0.13.1:** for the Bluetooth route of a console request the app sends the console wake advert (3.2), which needs no `n`, so it still works when the phone missed reports or the tag moved into a new epoch. The command form still goes by the routes above. Vectors: `commands`, `ble_commands` and `ble_console_cmd` in `lt2.json`.

`BLE_SCAN` is executed at once, in the RX window: the tracker scans, sends the BLE packets (2.3) as copies `j = 5…` of the report the command answered, and sleeps without a new window. The app finds them within a minute.

After executing, the tracker answers by 3.5: `CMD_ACK` and `cmd_seq` in report `n + 1`, and the flag stays set until a report carrying it was ACKed, at most three reports. It does not execute the same `cmd_seq` a second time (it only acknowledges again). A command is bound to `(n, k)` or `(n_a, k)`, so an old one cannot be replayed. **`cmd_seq` (0.10.0):** the app picks a random value from 1 to 255 whose low four bits differ from the `cmd_seq` bits in the tag's newest report and from its own previous command, so a second or restored device never repeats the tag's last executed number. "Confirmed" needs a report with a counter above the newest one when the command was queued, `CMD_ACK`, the command's low four bits, and for Lost, Track and Normal the mode the command asked for.

### 3.1 Command over Bluetooth advertising (0.7.7)

When the owner's phone is near the tag, a waiting command can reach it without the mesh. While a command is pending, the app puts it in the phone's Bluetooth advertising. The tag picks it up during a Bluetooth scan it already runs at a wake-up. The mesh path and the mailbox keep working unchanged, and whichever path arrives first wins.

**Payload.** It is a legacy advert, non-connectable and non-scannable, with one AD structure: manufacturer specific data (`0xFF`), company id `0xFFFF` (little endian `ff ff`), then 21 B:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | `0x22` (the command type, in clear) |
| 1 | 4 | `xc`, the command tag of section 3 for `(n, k)` |
| 5 | 8 | bytes 1…8 of the command ciphertext (`cmd_seq`, opcode, arguments 0…5) |
| 13 | 8 | `mac` |

These are the bytes of the sealed command `Pc` (section 3) for the same `(n, k)`, minus two parts. Plaintext byte 0 is always `0x22`, and bytes 9…16 are zero for every current opcode (`SET_IDLE` ends at offset 8). The tag rebuilds the full 29 B `Pc`: it derives `k_enc` for `(n, k)`, computes the keystream `AES-128-CTR(k_enc, IV = mac || 0⁸)`, sets ciphertext byte 0 to `0x22 ⊕ ks[0]` and bytes 9…16 to `ks[9…16]`. Then it opens `Pc` exactly like a command from the mesh: the same key `C_e(n)`, the same tag, the same MAC over the full plaintext. A command with a non-zero byte after offset 8 has no Bluetooth form and goes by mesh only. The AD structure is 25 B, so it fits a legacy advert (31 B) together with the flags that some stacks add. `lt_ble_command_seal/expand/open/find` (lt_core), `lt2.ble_command`, `ble_command_expand`, `open_ble_command` (Python), `BleCommand.payload` (Kotlin). Vectors: `ble_commands` in `lt2.json` (with the full `p` and the `ad` structure).

**Which `(n, k)`.** For a slot `k ≥ 1` the advert carries the bytes of the slot command for `(n_a, k)` (2.6, derived from `ks`), the same `Pc` the mesh window of that wake-up accepts, and the tag rebuilds it with `ks`. Any other wake-up uses `k = 0xFFFF` ("the next wake-up after report `n`"): normal reporting, the heartbeat of a quiet stretch, LOST. `0xFFFF` is keyed with `C_e(n)` of the tag's last report `n`, as `u16(k)` after `u32(n)` (`LT2-c || u32(n) || ff ff`). Checks never reach 4096, so a mesh command can never carry it. The window right after a report (`k = 0`) has no Bluetooth scan, so `k = 0` is never advertised.

**Addressing and privacy.** Every device nearby receives the advert, and only its tag can use it. The 4 B `xc` is the cheap filter. A tag computes the one `xc` it would accept at the start of its scan, and for every advert it walks the AD structures and compares 4 bytes. It does no cryptography unless the tag matches. `xc` changes with every check and every report, and only holders of `C_e(n)` can compute it, so an observer cannot link the adverts of one tag or one command across checks. Within one check interval the payload is constant. The tag matches on `xc` only and never looks at the advertiser's address, so delivery does not depend on it. Which address type Android uses for this non-connectable set is not yet checked on a phone (the app cannot choose it). We assume a random address that rotates, and the company id `0xFFFF` says only "LibreTag-like". The ciphertext reveals nothing without `C_e(n)` and the MAC stops forgery. A copy replayed later is bound to its `(n, k)` like a mesh command. It is useless after that check, and inside it the `cmd_seq` rule makes it a repeat.

**Tag side.** Since 0.9.3 every wake-up looks for the advert. A wake-up that has a presence scan (IDLE with known devices, anchors) or a LOST scan uses it, as before. Any other wake-up runs a **command scan**: passive, 100 % duty, 1.5 s, started with the wake-up, so alongside the LoRa check window of a listen-only wake-up between reports (2.1) or alongside the GPS search of a wake-up that looks (a check or a report without known devices, TRACK, LOST without a scan due). It keeps no device table and only compares the 4 B tag; a wake-up does not get longer (on a board without GPS the decision waits for those 1.5 s). On the ESP32 the SoC does not light-sleep during it, and a listen-only wake-up has no Wi-Fi scan, so the two radios do not meet; at a wake-up that looks the Wi-Fi scan comes first, as for the presence scan. Why 1.5 s: the phone advertises every 250 ms (+0…10 ms), so 1.5 s holds 5 or 6 advertising events; on the bench a Wio Tracker L1 heard 79 % of a neighbour's advertising events with this scan, so the chance of missing all of them is below 0.1 %. Before 0.9.3 the tag looked only in the presence and LOST scans, so not at listen-only wake-ups and never without known devices.

The presence scan itself gained radio time in 0.7.7 in two cases:

- When an anchor answers, the presence scan used to stop at once. It now runs at most 2 s longer, unless a command was already taken, because the anchor's advert may come before the phone's command advert. With `anchor gps off` the decision waits the same 2 s.
- Boards without GPS (the ESP32 tracker) have no search for the scan to run alongside. The presence scan now gets 3 s of its own after the Wi-Fi scan, only when the tag has anchors. Before this the scan stopped as soon as the Wi-Fi scan ended, so presence detection was unreliable there as well.

A command taken from an advert is handled like one taken at a check. The tag executes it (`BLE_SCAN` runs in the window after report `n + 1`), closes the check window and sends report `n + 1` with `CMD_ACK` when the search ends. At a listen-only wake-up it first looks (GPS, Wi-Fi, Bluetooth presence), as for a mesh command there. The same `cmd_seq` arriving later from the mesh (a timed or plain mailbox entry, the app's own radio) is only acknowledged again. The reverse holds as well. Console: `blecmd` prints `BLECMD n=<n> k=<k> tag=<xc> scan=presence|lost|check seen=<adverts with our tag> taken=<commands> scans=<command scans since boot> first_ms=<scan start to the last taken advert, -1 none>` for the next wake-up (0.9.3; `none` before). `blecmd adv <42 hex>` feeds a payload to the next wake-up's scan through the same filter (unlocked console, for bench tests).

**Phone side (app).** A tag qualifies when the app can command it (the app needs firmware 0.9.5 or newer). The app then advertises the pending command for the next wake-up that scans:

- With a known grid (2.6), slot `k` is advertised from the end of slot `k − 1`'s scan until `t_k + g_k + 45 s`, for each grid the app holds. The 45 s cover a 30 s presence scan, the 2 s grace and the flood delay of report `n`. After the last check it is `0xFFFF` while quiet, or `R` (`report_every`, the wake-up that reports) between reports.
- Without a plan (normal reporting, LOST, an approximate report time), `0xFFFF`.

It uses one advertising set per tag, legacy, 250 ms interval, medium TX power. With more tags than the phone has sets, they take turns every 8 s. The switch to the next check is woken by an alarm (`setAndAllowWhileIdle`), so Doze does not leave an old sealing on air. The app stops when `CMD_ACK` with the command's `cmd_seq` arrives, when the command is cancelled or replaced, when its mailbox lifetime ends (1 h for a beep, 48 h for LOST and the interval, 12 h for the rest), when Bluetooth is off, and when Android 12+ has not granted "Nearby devices" (`BLUETOOTH_ADVERTISE`). The app asks for that once, after a command is queued for a qualifying tag. If the phone does not know report `n` (it missed it), its sealing is for an older `n` and the tag ignores it. The mesh mailbox delivers the command as before. **App 0.12:** while the tag is late (its expected report has passed), the app also advertises the same command sealed for `n + 1`, in case report `n + 1` went out and was lost (typically the one `QUIET` report before a long stretch near the owner): `k = 0xFFFF`, and with a known interval the checks of `n + 1` around now, counted from `t0` = the expected time of `n + 1` with the owner heartbeat (the current check and its two neighbours). That is up to four more sets per tag; with more sets than the phone runs at once, a late tag's sets take turns every 2 s instead of 8 s (`BleBeaconPlan.ahead`, docs/design/tag-diagnosis.md 4.1). Nothing changes on the tag. Not yet checked on the bench: how many sets the test phones run and whether the 2 s turns reach the tag's 1.5 s scan.

**Why legacy, compact.** The sealed command is 29 B, and a legacy advert has 31 B. A 16-bit service data or manufacturer AD leaves 27 B for content, and the flags take 3 more on connectable adverts. So the full `Pc` does not fit, but the two bytes the receiver can rebuild are free to leave out. Extended advertising (BLE 5) would carry `Pc` whole. Both the nRF52840 and the ESP32-S3 can scan it, but the tag would need `CONFIG_BT_EXT_ADV` (RAM and flash on the nRF), and not every Android phone advertises extended PDUs. Legacy adverts are also what the tag's existing passive scan already receives. A short "command waiting" beacon that makes the tag connect or listen longer would cost the tag more radio time and add a GATT server, and it would still need a key-derived identifier. The compact form uses no extra radio time, needs no connection and keeps the mesh command's security unchanged.

### 3.2 Console wake advert (0.9.5)

The owner stands next to the tag and wants its Bluetooth console (6.2). A `BLE_CONSOLE` command advert (3.1) does not always get there. It is sealed for `(n, k)`, where `n` is the last report the phone heard. If the tag was out of mesh range for a while, its `n` has moved on, often into a new epoch whose old `C_e` it has erased, and its `xc` filter never matches. The wake advert is keyed with `usb_key`, which the tag keeps as long as it is paired, so it works whatever `n` the tag has reached.

**Payload.** A legacy, non-connectable advert from the phone with one AD structure: manufacturer specific data (`0xFF`), company id `0xFFFF` (little endian `ff ff`), then 13 B:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | `0x26` |
| 1 | 6 | `salt`: 6 random bytes chosen by the phone, new for every advertising session |
| 7 | 6 | `HMAC-SHA256(usb_key, "LT2-bcon-wake" ‖ salt)[0:6]` |

The AD structure is 17 B (`10 ff ff ff 26 …`). `lt_bcon_wake`, `lt_bcon_wake_match`, `lt_bcon_wake_find` (lt_core), `lt2.bcon_wake`, `bcon_wake_match`, `bcon_wake_find` (Python). Vectors: `bcon_wake` in `lt2.json`: `valid` (salt, tag, payload and AD structure for four salts), `invalid` (payloads that must not match: another key, a changed salt or tag, type `0x25`, 12 and 14 B, the console advert's tag) and `find` (AD bytes and the payload the finder returns, or `null`).

**Tag side.** Every scan that looks for a command advert (presence, LOST and the command scan of 0.9.3, so every wake-up) also looks for a wake advert. The scan callback walks the AD structures and compares company id, length and type byte. It keeps no device table and does no cryptography there. The main loop drops a candidate whose salt it took before in this boot (it keeps the last 8) and otherwise computes one HMAC, at most 16 per scan. A match opens the console window for 180 s under the rules of a `BLE_CONSOLE` command: a locked tag, above the transmit floor, not closed after 5 failed handshakes; `blecon boot off` and the resets in a row do not apply, because the owner asked. If the window is already open, the advert is ignored. It sends no report, needs no `n` and gets no acknowledgement: the app sees the tag's console advert (6.2) instead. The window opens at the tag's next wake-up, so the owner may wait up to one wake-up interval. The command path of 3.1 is unchanged. Console: `blecmd` adds `wake_seen=<wake adverts checked> wake_taken=<windows opened>`, and `blecmd adv <26 hex>` feeds a wake payload to the next scan (unlocked console, for bench tests).

**Privacy and replay.** The salt is new for every session, so adverts of two sessions cannot be linked without `usb_key`. An observer learns that a LibreTag-like phone wants a console here, not for which tag. A copy replayed in the same boot is refused by the salt ring. After a reboot a replay can open a window, but the window still needs the `usb_key` handshake (6.2). The most it costs the tag is 180 s of advertising.

### 3.3 ACK (0.10.0)

The owner's app confirms a report with a 13 B ACK sealed with the command chain. Only a holder of `C_e(n)` can make one: the owner and a control share. A view share cannot, and neither can a bridge. An ACK says "a device holding the command key opened report `n`"; the app makes it only after the report's mac checked out.

```
ka  = HMAC(C_e(n), "LT2-a"  || u32(n) || u16(k))
xa  = HMAC(C_e(n), "LT2-ax" || u32(n) || u16(k))[0:4]
ct  = info XOR ka[0]                             # 1 B
mac = HMAC(ka[16:32], xa || ct)[0:8]
Pa  = xa || ct || mac                            # 4 + 1 + 8 = 13 B
```

`u16(k)` is always appended, also for `k = 0`. `k = 0` is the listen window right after report `n`; `k ≥ 1` is slot `k` of the tag's grid (2.6), and the ACK is still for the tag's last report `n`.

| `info` bits | Field |
|---|---|
| 0–3 | `hold`: how long the tag may go without the next ACK before a report has to arrive, in units of 3 h. 0: every report has to arrive (a guarded tag). The app writes 4 (12 h) by default and offers 0, 2, 4, 8 (0, 6, 12, 24 h). A tag never uses less than one report period plus 5 minutes for a non-zero `hold` |
| 4 | `MORE`: a command follows, keep the window open (no early sleep). At a slot that only listens, a tag that takes an ACK without `MORE` keeps its receiver on 1 s more and then sleeps, so a command a bridge sends 300 ms behind the ACK still lands. The app sets `MORE` while a command waits; timed ACK entries it published before a command was queued are deleted and published again with `MORE` for the slots still ahead (4.3) |
| 5 | `ROUTED`: the routed form, followed by a path (below). 0 = the near form |
| 6–7 | 0. A tag refuses an ACK with either set |

**The tag's check.** It computes the one `xa` it would accept in the current window (its last report `n`, the current `k`) and compares 4 bytes before any other work, then the mac, then the reserved bits. A second copy in the same window changes nothing. After the window an ACK matches nothing. A forgery passes with chance 2⁻⁶⁴ per try.

**Near form.** `Pa` alone, `ROUTED` 0, always sent zero-hop. On `#libretag`: datagram 13 B, MeshCore plaintext 16 B (one block), `GRP_DATA` payload 19 B, packet 21 B (header `0x1A`, `path_len` with count 0), 162 ms. Stealth: `Pa` followed by 6 random bytes, 19 B, the same length.

**Routed form.** `ROUTED` 1 and the bridge appends the path the tag should use:

```
datagram = Pa || pl || path        # 13 + 1 + (1 or 2) × hash size = 15 to 20 B
pl       = (hash_size − 1) << 6 | count       # MeshCore's path length byte; count 1 or 2
path     = repeater hashes in the order tag to bridge
```

MeshCore plaintext 32 B, packet 37 B plus the path left in the header, about 215 ms per transmission. The bridge sends it DIRECT along the reversed path (bridge to tag), so the last repeater delivers it with an empty path. Stealth: padded with random bytes to 35 B, the length of a command's payload; the tag reads `pl` to find the end. The `ROUTED` bit is under the mac, so nobody turns a routed ACK into a near one or back. The appended path is not: the app does not know it, and a path never goes through Nostr. The tag refuses a routed form without a path, a path after a near form, 0 or 3 and more entries, a reserved hash size, and a length that does not match `pl`. It takes a routed ACK only when the packet came on a DIRECT route with an empty path. Vectors `acks`, `acks_routed`; `quietmesh.ack_seal`, `ack_open`, `ack_routed`.

**What the tag does with it** (SPEC 3.2): a near ACK sets the link to NEAR, a routed ACK to ROUTED and stores the path (at most 2 hashes of at most 3 B, with the hash size and the fix where it was learned). If the tag already took a near ACK for this report it ignores a routed one; a near ACK after a routed one drops the path. The `hold` bits of a routed ACK are not used.

**What a malicious bridge can do.** It cannot make an ACK. It can drop the report or the ACK (the tag floods: more airtime, not less visibility), replay an ACK in range inside the same window (true anyway), relay hello and ACK over a long link (then the report really was delivered), jam the ACK (bounded by the IDLE flood budget), or resend a routed ACK it heard with a wrong path in the same window: the tag stores a path that leads nowhere, its next routed copy gets no ACK, and it floods and forgets the path. One late report. Stripping the path to fake a near ACK does not work, because `ROUTED` is sealed.

No Bluetooth form in this version.

### 3.4 Routes per packet and direct routing (0.10.0)

Order of preference, by the number of repeaters that transmit: zero-hop (none), along a known path of 1 or 2 repeaters, a flood in an area scope, the country scope, unscoped. Rules:

- **Zero-hop** is DIRECT with an empty path (header `0x1A`, `path_len` = hash size bits and count 0). No repeater forwards it; every node in range processes it. DIRECT packets carry no transport codes and are never region filtered.
- **Along a path** is DIRECT with the path in the header in send order. Each repeater whose hash is the first entry removes it and retransmits; the last one sends the packet with an empty path, which every node in its range processes. Nothing reports a broken path, so every send along a path needs a confirmation and a flood fallback.
- **The hop count of a DIRECT packet is unknown to a receiver.** A zero-hop packet and a packet that came along a path both arrive with an empty path. Only a flood with an empty path has 0 hops. "Heard directly" means: arrived on a DIRECT route, or as a flood with 0 hops. Route types are `flood`, `tflood` (scoped flood), `direct`, `tdirect`; a receiver accepts all four.
- **Every second try is other bytes.** Repeaters mark a payload as seen before they decide to forward it, whatever the route. A report's second try is another copy `j`. A command's fallback send uses channel data type **`0xFF6C`** instead of `0xFF4C`; the tag accepts a command under either (vectors `retry`). In stealth the random padding already differs.

| Packet | NEAR (a bridge or the owner's node in direct range) | ROUTED (path of 1 or 2 repeaters, tag standing) | FAR |
|---|---|---|---|
| routine report | copy 9 | copy 9 (finds a bridge or node that came into range) | copy 9 |
| report that has to arrive | copy 9; without ACK a flood (copy 0, then copy 10) | copy 11 along the path; without routed ACK a flood | flood copy 0, then copy 10 |
| report from a new place | copy 9, then a flood at the next check (IDLE) or after 12 s | flood; the path is forgotten | flood |
| Wi-Fi and BLE packets, low-battery DM | zero-hop when their report was ACKed so | along the path when their report was ACKed so | flood |
| discover | zero-hop | zero-hop | zero-hop |
| ACK from a bridge | zero-hop, near form | along the reversed path, routed form | none: a flood heard over 3 or more hops gets no ACK |
| ACK from the owner's node | zero-hop | not sent | not sent |
| command from a bridge | zero-hop; with `both` a fallback flood 12 s later | along the reversed path; fallback flood 12 s later | flood in the report's scope |
| command from the owner's node | zero-hop | not sent (the mailbox carries it) | not sent |
| blind LOST command (4.3) | | | flood from a named bridge, country scope or unscoped |

**Paths.** A path is the list of repeater hashes a flood copy collected on its way to a bridge, `[R1, R2]` with `R1` the repeater that heard the tag. The tag sends copy 11 along `[R1, R2]`, the bridge sends along `[R2, R1]`. At most `direct_max_hops` entries (2; 0 turns direct routing off in a bridge). A path lives in the bridge's ledger and in the tag, never in a Nostr event. The owner's node never routes: a route that ends at a phone is wrong as soon as the phone moves. A moving tag never gets or uses a path: the app offers the routed form only when the report's fix is within `MOVE_M` (300 m) of the previous report's.

**The tag** forgets its path when it moved (a fix farther than `MOVE_M` from where it learned it), when one routed copy was not confirmed, when a near ACK arrived, and when the home network changed. Without a fix it keeps it and lets the confirmation decide. A routed copy is not a flood: it does not count in `floods_24h` or the IDLE budget, does not move `lvl` and is not followed by copy 10. A ROUTED tag still sends its zero-hop hello every report period, because a node that comes into range does not process a packet that still has path entries.

**Waits.** After the cheap copy, where the decision is immediate (TRACK, LOST, events, command answers, a guarded tag): 12 s after a hello, 12 s plus 1.5 s per hop after a routed copy (a field walk measured 0.6–1.2 s added per repeater hop; 1 s per hop before). In IDLE for a moved tag or a heartbeat, the next check. A bridge's fallback after a zero-hop send with `both` or a send along a path: 12 s without a report that answers it (4.3). At a slot the first send is at `t_k + 1 s` and the fallback at `t_k + 13 s`.

Reference: `quietmesh.plan` (the bridge's choice per entry), `quietmesh.arrival` (what a receiver may conclude). Vectors `plan`, `copies`.

### 3.5 The answer to a command (0.10.0)

`CMD_ACK` is a flag in a report, not a packet. A command gets exactly one report with `CMD_ACK` and the command's `cmd_seq`, and the flag stays set in the following reports until a report carrying it was ACKed, at most three reports. When the answer goes out:

| Command | Arrived on a DIRECT route (zero-hop, or the last hop of a path), or needs no position | Arrived as a flood |
|---|---|---|
| Beep, Bluetooth console, Normal (`SET_MODE` idle), settings, `SET_AREA`, `BLE_SCAN` | within 2 s, the last position (no `HAS_FIX`), no GPS search, by the link state | the same |
| Lost, Track | within 2 s as on the left, then the mode's first report with a fresh fix | no quick answer: the mode's first report after the GPS search carries `CMD_ACK` |

A quick answer also leaves while a GPS search of the same wake-up runs; the search goes on and is neither stopped nor restarted for it. The answer goes by the link state like any report that has to arrive: zero-hop first in NEAR, the path first in ROUTED, a flood in FAR.

A command never changes the link state, `t_ack` or the path. A command along a path arrives exactly like a zero-hop command, so it says nothing about range. Only an ACK does.

## 4. Nostr (bridges and app)

Bridges publish what they catch in the `#libretag` channel (SPEC 6.2, variant B). They decrypt nothing and do not know `K0`.

**Report:** kind `4243`, tags `["y", hex(x)]`, `["expiration", "<now + 14 d>"]`, `content = base64(P)`. Signed with a **random key for each event**. `created_at` is the time the bridge's radio heard the packet (not the time after the random delay below): apps anchor a quiet tracker's check schedule (2.1) on it. Before publishing, the bridge waits a random 2 to 5 s (0.10.0: 0.3 to 0.8 s for a report heard directly or over 1 or 2 hops with a path, when no untimed command entry waits for its `x`), and if in the meantime it sees an event on the relays with the same `y` and the same content, it does not publish. The app queries with the filter `{"kinds": [4243], "#y": [window tags]}`. **Approximate time (bridge 0.3.1; Android bridge 0.6.0, Python bridge 0.7.0: every frame whose receive time is more than 20 s old, or that the node marks `queued`):** a frame that a companion node queued while no bridge was reading it (the first drain after a connect or reconnect) was heard at an unknown time. The bridge still publishes it. `created_at` is the latest possible time, when the bridge drained it, and an extra tag `["approx", "<unix s>"]` carries the earliest: the last time the bridge saw the node's queue empty, or `created_at` if it never did. Apps subscribe with `since` and relays apply that filter to live events too, so a `created_at` in the past would never reach a live subscription. An app takes the report's time as the range from the `approx` value to `created_at`. It must not anchor a check schedule on such a report, and an exact copy of the same report replaces it. The frame never triggers a command. Bridge 0.3.0 had the two values swapped, so apps use the smaller one as the start of the range.

**Command mailbox:** kind `4244`, tags `["y", hex(x of the report)]` for each copy `j` (five since 0.10.0), `["route", "near" | "direct" | "flood" | "both"]` (4.3), `["expiration", "<now + 48 h>"]`, `content = base64(Pc)`. Published by the app in advance for several following `n`, signed with the mailbox key `sk_n` of the report it answers (4.2), with `["v", "2"]` and the targeting tags of 4.1. The bridge keeps the tags of pending commands, and when it catches a report with the same `x` on the radio, it transmits `Pc` once, by the plan of 4.3 (zero-hop, along a path, or a flood in the report's scope, with the fallback of 4.3). It transmits a command it knew **before** catching the report, on the **first** hearing of that `x` on its radio (a later copy of the same report does not trigger), or a late entry from the locked key (4.2). Only entries from a key the report locked count (4.2). When several of them match, it transmits the one it **saw first**. A replaced command is deleted by the app (NIP-09), so the old entry does not linger. The bridges agree over Nostr on who transmits (ephemeral kind `24244`, tag `y`, fewer hops wins, then the smaller `SHA-256(pubkey || x)`; since 2026-11-18 only claims from known bridges count, see "Claims" below).

**Timed mailbox entries.** A command for slot `k` of the anchor `n_a` (2.6) carries two more tags: `["at", "<unix s of t_k + 1>"]` and `["via", hex(x of a copy of n_a)]`, one `via` per copy of the anchor the app has. A bridge that caught a `via` keeps its hop count, path and scope for 48 h from the last use (4.3); at `at` it transmits `Pc` by the plan of 4.3. A bridge that did not catch report `x` sends nothing: it has no sign that it is near the tracker. `at` is when the command should arrive; a sender may transmit somewhat earlier by its own estimate of the flood delay, but the tracker's window opens only `g_k` before `t_k`, so too early misses it as surely as too late. Coordination over `24244` as above. An entry without `at` keeps the 0.6 behaviour (send when the report with `y` is caught). The app publishes entries for the next 3 slots, then every 3rd slot until the command's lifetime ends (LOST: every slot for the first 6 h), for every grid it holds (2.6), each sealed for its own `(n_a, k)`, and lets them expire shortly after their `at`.

**Cancelling a mailbox command.** Every `4244` event for report `n` is signed with `sk_n` (4.2), which the app derives again when it needs it, so it stores no keys. To cancel, it publishes a NIP-09 deletion for every event of the command (plain and timed entries), signed by that event's own key (`sk_n` of its report): kind `5`, tags `["e", <id of the 4244 event>]`, `["k", "4244"]`, `["expiration", <the same as the 4244 event>]`, empty content, to the same relays. The expiration lets relays drop the deletion together with the event it removes. A bridge subscribes to `{"kinds": [5], "#k": ["4244"], "since": <now − 48 h>}`, accepts a deletion only when its pubkey equals the pubkey of the `4244` event, drops the entry if it has not transmitted it yet and publishes no claim for it. It remembers the deletion, so a `4244` event that arrives after its deletion is not added. A command already transmitted stays transmitted. The app subscribes to claims (`24244`) with the `y` tags of its pending events; a claim means a bridge is about to transmit, so the app shows the command as sent and no longer offers to cancel it, as when its own radio sent it. The app also sends these deletions by itself. Once the command is acknowledged, it deletes every remaining entry; left in place, they would repeat the command on air at the next reports and check times. When a newer report `n` arrives while the command waits, it deletes the entries sealed for earlier reports. An untimed one waits for a report that has already passed (a reboot or a long quiet stretch makes the counter jump), and a timed one targets the checks after an older report, where the tag no longer listens. The entries for `n` stay: a bridge may be transmitting one in that report's window, and a deletion that arrives during its claim would stop it.

**No proof of work (2026-11-18).** Entries carried NIP-13 work from 2026-11-17 until the signed mailbox (4.2) replaced it: a GPU did the 16 to 28 bits in microseconds, so work never priced anything, and a signature with the key the report commits to tells the owner from a stranger, which work cannot. An entry with `created_at` more than 60 s in the future is refused (`future_max_s`).

**Limits on timed entries and on the mailbox.** A bridge applies, with configurable defaults:

1. `at` must not be in the past (beyond the 60 s tolerance above) and, when the bridge has heard report `via`, it must lie between that report's receive time and `heard_at(via) + 25 h` (the longest heartbeat, 24 h, plus 1 h). Checked when the entry arrives and again before sending, so an entry that came before its report is still bounded. A bridge that never heard `via` sends nothing. Untimed entries (the ones for upcoming reports that answer a tracker coming back) are not affected.
2. At most **12** unsent timed entries per `via`. Over that, those seen first stay. Once report `via` locked its keys (4.2), an entry from any other key is refused on arrival.
3. At most **one** timed transmission per `via` per **10 min**, and at most **20** timed transmissions per rolling hour in all. The 10-minute gap does not apply to an ACK, nor to the second entry of a multi-grid send (2.6).
4. `#libretag` has its own receive limit (new packets per minute; copies of a packet already heard do not count) and its own airtime budget, separate from the budget for DMs and Roadbeacon, so a flood on `#libretag` cannot silence the other channels. The Python bridge keeps both budgets in its ledger, so a restart does not reset them.
5. A full mailbox evicts the oldest inserted entries first (not the ones expiring first, which would let long-lived spam push out a 1 h Beep). The relay an entry first came from holds at most about a third of the mailbox.
6. An identical `Pc` goes on air once, whatever event carries it (a copy of the owner's command under a stranger's key, time and `via` is never sent a second time). A `Pc` heard on air counts as sent.

**Command groups and "done" (bridges from 2026-11-17).** All `4244` entries of one command (the plain ones and the timed ones) carry the same `["g", "<16 lowercase hex>"]`, random per command. A malformed `g` makes the event invalid. Timed entries are bound to report `n`: as soon as the tracker sends report `n + 1` (with `CMD_ACK` after executing the command, or for any other reason), every remaining timed entry of the group is useless, but without the owner's app nobody stops the bridges from flooding them at their checks. A bridge therefore drops the unsent timed entries of group `g` (plain entries stay: the plain entry for `n + 1` still goes out, and a tracker that already executed the command only acknowledges it again) when one of these holds:

- **Next report (0.10.0).** It hears, live (not a stale queued frame), a 45 B report whose `x` is a `y` of another untimed entry of group `g` than the one `via` belongs to, on any route and with any hop count. Only the owner can compute that `x`, so the report is the tracker's own. A `y` of the same entry as `via` (a sibling copy of the same report) counts only 120 s or more after `via`.

The bridge then remembers `g` as done (a timed entry of `g` that arrives later is not added) and publishes a **done claim**, ephemeral kind `24244` without `y`/`hops`: tags `["g", g]`, `["done", hex(x of that report)]`, signed with the bridge key (a bridge without one uses a random key), empty content. Older bridges ignore it (no `y`). A bridge that receives a done claim (valid signature, `created_at` within 30 s) drops the unsent timed entries of `g` only with its own evidence of report `x`: heard on its radio, or a verified kind `4243` with `y = x` on its relays, and `x` is a `y` of an untimed entry of `g` (seen before the claim). The app may subscribe to `{"kinds": [24244], "#g": [g]}` to learn the same.

What a forged done claim can do: someone who reads `g` and the plain `y` tags from the relays and also publishes a fake `4243` for one of those `y` makes the bridges drop the remaining timed entries of that command. The plain entries still deliver at the next report, and the app sees the claim, so the cost is a later delivery and the command is not lost. Someone who owns a tracker could likewise add a plain entry with the victim's `g` and their own tracker's next `x`. Both are cheaper to do than to defend against without the tracker key; the rules above keep an honest bridge from dropping a group on a coincidence (another tracker reporting nearby).

### 4.1 Bridge keys, announcements, receipts and targeted entries (2026-11-18)

Background and the attacks this answers: `docs/design/bridge-market.md` (A.5, B). Kind numbers `4245` and `38244` were checked against the NIP list on 2026-11-18 and are not taken. Vectors: `host/tests/vectors/mailbox-v2.json` (copied to `android-bridge` and the app), made by `uv run python -m nostrmesh.market vectors`.

**Bridge key.** A bridge may have one stable Nostr key (Python `[bridge] key`, a file with a hex key or nsec, mode 600; `nostrmesh bridge-key` makes one). It signs the bridge's claims, done claims, receipts and announcements. Reports (kind `4243`) keep a fresh random key per event, as before. A bridge without a key works as before, but its claims count nowhere (below) and it publishes no receipts and no announcement.

**Announcement**, kind `38244` (addressable), author = the bridge key, one per network the bridge serves:

```
["d", "<network>"]          e.g. "sk"; "" when the operator names none
["k", "4244"]               service: the LibreTag mailbox
["region", "<scope>"]       repeated, narrow first: the MeshCore scopes it listens in and floods in (0.10.0); absent = the node's default scope
["radio", "up" | "down", "<unix s since>"]   0.10.0: the state of the radio itself (SPEC 3.2), not of the software
["preset", "<freq Hz>", "<bw Hz>", "<sf>", "<cr>"]   when the node reports it
["relay", "<url>"]          each relay it reads entries from
["signed", "<anchor_lead_s>", "<late_max_s>"]   the signed mailbox of 4.2 and its two times, e.g. "60", "60"
["open", "1" | "0"]         it serves open entries (no "p")
["receipts", "1" | "0"]     it publishes receipts
["expiration", "<now + 7 d>"]
content: JSON {"name": "...", "version": "...", "adapter": "...", "zero_hop": bool, "direct": bool}
```

Published at start, every hour (0.10.0; every 24 h before) and within a minute of a change of the radio state, so the app can tell "the bridge is offline" (an announcement older than 2 h, or `radio down`) from "the tag is silent". A bridge that stops disappears within 7 days. A relay with a kind allowlist has to accept `38244` and `4245` (and `24244`, `4243`, `4244`, `5`) for this to work through it. It carries no position. Everything in it is the bridge's own claim. A network name is `[a-z0-9-]{1,32}`.

**Receipt**, kind `4245`, author = the bridge key, when the bridge hears a 45 B report live (not a queued frame) for the first time **and heard it directly** (0.10.0): on a DIRECT route (`["route", "direct"]`, no hop count, because the bridge does not know it) or as a flood with 0 hops (`["hops", "0"]`). Also `["y", hex(x)]`, `["expiration", "<heard + 48 h>"]`, `created_at` = the time the radio heard it, empty content. No receipt for a flood heard over one or more hops. It goes out together with the report event, at most 120 an hour, on by default (`receipts`). The app uses it to address the ACK and the commands for a NEAR tag to that bridge (`p`). The app asks `{"kinds": [4245], "#y": [x of its tag's recent reports]}` and learns which bridges hear the tag and how near. The tag transmits nothing more for this: a receipt only says that some report with this `x` reached this bridge directly, and `x` changes with every report and links to nothing for anyone without the view key. A receipt is not proof: a fake bridge can copy `x` from the relays.

**Targeted entries (format 2).** Every entry carries `["v", "2"]`, and then:

- `["route", ...]` is binding: the table and the plan in 4.3. An entry its route does not allow is not sent and its `y` is left for a nearer bridge.
- `["p", <bridge pubkey hex>]`, 0 to 4 of them: only these bridges may transmit it, in order of preference. A bridge not named does not store the entry.
- `["r", <network>]`, at most one: the network the tag is in. A bridge that names its networks stores only entries for those networks (or without `r`). The app takes `r` from the announcements of the bridges that heard the tag and leaves it out when they disagree or when none are known.
- No `p`: an **open** entry. Any bridge that hears the tag may send it, if it serves open entries (`accept_open`, on by default).

An entry without `["v", "2"]` is refused (format 1, apps before 0.11, is gone since the signed mailbox). Every bridge subscribes to all `4244` and drops on arrival what is not for it. A bridge that serves no open entries keeps those that name it in `p` or its networks in `r`, the ACK entries (4.3) and the anchors (4.2). It cannot ask the relays for less: an anchor carries no tag a filter could select, and without the anchors no key locks, so no ACK entry could ever go out from it.

**Claims (kind `24244`).** A bridge with a key signs its claims with it. A claim for an untimed entry also carries `["proof", hex(SHA-256(P || pubkey))]`, where `P` is the report packet the bridge heard (45 B) and `pubkey` its 32 B key. `P` reaches the relays only 2 to 5 s after the report (the publish delay floor is above the 1.5 s claim wait), so only a bridge that heard the report on its radio can make the proof in time. A bridge counts a rival claim when:

- it comes from a configured peer (`peers`, keys the operator trusts), or
- the entry is untimed, the claim's key has an announcement (or is named in the entry's `p`), and its `proof` matches the `P` this bridge heard.

Every other claim is ignored. That includes claims from random keys (bridges before 2026-11-18) and, for timed entries, claims from anyone but a peer: a timed entry has no secret to prove hearing with. The worst case of an ignored claim is a second transmission of the same `Pc`, and repeaters merge identical packets. Among counted claims the winner is the one with the lowest `(index in p, hops, SHA-256(pubkey || x))`; for an open entry the index is 0 for everyone. A bridge publishes its claims without waiting for a relay to accept them. The claim round before an untimed send is 1.5 s; before the first routed ACK of a flood it is 2 s (4.3). Done claims keep their own evidence rules and are signed with the bridge key too. The app shows a command as sent only for a claim whose key has an announcement.

**Airtime order.** Inside the `#libretag` budget (0.1 % of an hour), timed transmissions may use at most half (`timed_airtime_share`), so the rest stays for commands that answer a report. Floods of open entries are capped at 6 per rolling hour (`open_floods_per_hour`); zero-hop and entries that name this bridge do not count, a fallback flood of an open entry does. The cap is checked before the claim round; otherwise a bridge that may not send could win the round and keep the others from sending.

**The owner's own node.** The app also sends a waiting command from the owner's own radio through MeshCore Open's Local API (section 3, "Route"; the Local API protocol is defined in [MeshCore Local API](https://github.com/jooray/meshcore-local-api)). That path carries `Pc` straight to the radio, with no Nostr event, so it needs no signature check and no bridge.

**Mailbox size.** A bridge keeps up to 200,000 tags (was 10,000). A relay that carries LibreTag should rate-limit kind `4244` per source: burst 120, then 60 a minute, with anchors (empty content) and ACK entries counted apart from commands. `host/deploy/strfry-mailbox-policy.py` is a reference strfry write policy that does this and accepts everything else unchanged (it can also demand NIP-13 work, off by default since 4.2). A relay that allows only listed kinds must allow `4243`, `4244`, `4245`, `24244` (ephemeral) and `38244`, and should accept the expirations these events carry: up to 15 days for `4243`, 51 hours for `4244`, 49 hours for `4245` and 8 days for `38244`.

**Region.** Every bridge sets the scopes it serves (`[radio] regions`, narrow first, the names from the node's region catalogue, e.g. the area scope and `sk` in Slovakia). It replies to a report in that report's scope (4.3) and uses the narrowest for a flood that answers a DIRECT arrival. A Local API bridge checks the name against the node's `regions.list` at start; an unknown name is dropped with a warning (the node would refuse every send), and a bridge without a region says at start that it floods in the node's default scope.

### 4.2 Signed mailbox (firmware 0.9.0, app 0.11.0, bridges 0.5.0; 2026-11-18)

Background: `docs/design/signed-mailbox.md`. A bridge has no key of the tag, so before this it could not tell the owner's entry from a stranger's copy of the owner's public `y` tags. Now every report commits to a key that only holders of the command chain can sign with, and a bridge transmits only entries signed by that key. Nothing is added on air: the report stays 45 B (section 2, sealing v2).

**Keys.** `sk_n = HMAC(C_e(n), "LT2-mb" || u32(n)) mod N` (0 becomes 1), `pk_n = sk_n · G` x-only. Every `4244` event for report `n` is signed with `sk_n`: anchors and untimed entries naming `y = x(n, j)`, timed entries with `via = x(n, 0)`, late entries, and the NIP-09 deletions of all of them. Keys of two reports are unrelated HMAC outputs and link nothing that `y`, `via` and `g` do not link already. Owner and control share (it holds `C_e`) derive the same key; a view share (only `V_e`) cannot. The report carries `c = SHA-256("LT2-mbc" || pk_n || x || ct || mac)[0:3]` at `P[4:7]`. Vectors: `mailbox_keys` and `reports[].pk` in `lt2.json`; `lock` and `events` in `mailbox-v2.json`.

**Anchor.** A `4244` event with empty content that names the next reports' tags, so the bridge knows the key before the report:

```
kind 4244, pubkey pk_n, content ""
tags: ["v", "2"], ["y", hex(x(n, j))] for j = 0, 1, 9, 10, 11, ["expiration", "<covering the counters ahead, up to 50 h>"]
      plus the "p" / "r" targeting tags of 4.1 (no "route", "g", "at" or "via")
```

An untimed command entry is an anchor too. The app keeps anchors published, whether a command waits or not, for the counters of 4.3 (16 ahead in IDLE, 24 in TRACK and LOST, the two checkpoint counters a reboot lands on, the start of the next epoch). It publishes the missing ones and renews those that run out whenever a report arrives or it syncs. It spreads their `created_at` and does not delete superseded ones (they expire).

**Lock.** When a bridge first hears `P` (45 B, live, on its own radio) at `t` (or earlier, when a kind `4243` with this `y` reached it from a relay first, by that event's `created_at`), it takes every key that named `y = P[0:4]` in an anchor or an untimed entry it knew at `t − anchor_lead_s` or earlier (default 60 s), and checks `SHA-256("LT2-mbc" || pubkey || P[0:4] || P[7:45])[0:3] == P[4:7]`. Every key that passes is **locked** for `x`. A key cannot be chosen to fit `c` in advance (it depends on `ct` and `mac`), so each event a stranger stored before the report is one guess with chance 2⁻²⁴. After the report a fitting key takes 2²⁴ trials, under a second, but it was not there `anchor_lead_s` earlier. A copy of `P` with another `c` (someone re-sending it to fit his own pre-posted key) is checked the same way: it can add his key, never remove the owner's, and each locked key gets at most one transmission per report.

**What goes out.** Only entries from a locked key, and nothing at all for a report without a lock (strict, from the start: there is no fallback to unsigned entries):

- **Untimed:** known before the report was heard, from a locked key, sent on the first hearing (4, "Command mailbox"); one per key and report.
- **Late entry:** an untimed entry from a locked key that arrives after the report. The bridge sends it at once while the report is at most `late_max_s` old (default 40 s since 0.10.0; the tag listens 60 s). The app publishes one only while the tag's listen window is open, for a command queued right after a report.
- **Timed:** only from the key report `via` locked (checked when due). Once `via` is heard, a timed entry from another key is refused on arrival.
- After a report locked its keys, a new entry for it from a key that could never lock (not locked, not known `anchor_lead_s` before) is refused, and stored ones from such keys are dropped.

A bridge keeps at most `keys_per_y` keys (default 8) per tag in anchors and untimed entries; the first seen stay. The owner's anchor names a `y` before anyone else can know it, because only holders of `V_e` can compute `x`.

**What it does not fix.** Claim jamming (bridge keys and proofs of 4.1 answer it), a flood that evicts anchors from a full mailbox (bridge-market.md gap 4: caps, relay limits and targeting answer it), and a stolen tag, which holds the current `C_e` and can sign for its own future reports. A view share that can guess a stationary tag's next plaintext can fit a key to a guessed `c`: each guess is one event, the prize one junk packet the tag rejects.

### 4.3 Quiet mesh entries and notes (0.10.0)

**ACK entry.** Kind `4244`, signed like every entry for the report it names (4.2), `["v", "2"]`, `["a", "1"]`, content `base64` of the ACK bytes:

| Entry | Tags | Content |
|---|---|---|
| live, for a hello (copy 9), or a flood copy of a tag that moved | `["y", x of the copy opened]`, `["route", "near"]`, `["expiration", now + 600]` | near form, 13 B |
| live, for a flood copy of a standing tag | `["y", x]`, `["route", "direct"]`, expiration as above | near form then routed form, 26 B |
| live, for a routed copy (copy 11) | `["y", x of copy 11]`, `["route", "direct"]`, `["via", x of the path record]`, `["p", the bridge that sent the previous routed ACK]` | routed form, 13 B |
| timed, for a report the app opened late | `["at", t_k + 1]` of slot `k` on the anchor's grid, one `["via", x]` per copy of the anchor it has, `["route", ...]` as above, `["expiration", at + 120]` | `Pa(n, k)` in the form of the rows above |

A live entry is signed with `sk_n` of the report it ACKs. A timed entry is bound to its `via`, so it is signed with `sk` of the anchor report, like every timed entry. `["p", bridge]` goes on the entry when a receipt named the bridge that heard the copy within 500 ms; the app does not wait longer. Timed ACKs: at most 2 slots for the near form, 1 for the routed form, and the app deletes them once a newer report arrived. A command queued after timed ACKs without `MORE` went out makes the app delete them and publish them again with `MORE` for the slots still ahead (the PWA too while it is open). Vectors `ack_entries`.

**A bridge and ACK entries.** An ACK entry passes a bridge that serves no open entries (`accept_open` off) and needs no `p`, because it can never cause a flood. It is stored only when its key can lock (4.2), and it is sent from the persisted lock and path store, so it works across a restart. The bridge plans the send as `quietmesh.plan` does (vectors `plan`):

- **Near form**: only zero-hop, only from a bridge that heard that copy directly (a flood with 0 hops, or a DIRECT arrival when the entry says `near`). No claim. The bridge waits a random 100 to 600 ms and skips the send if it heard the same `Pa` on air meanwhile.
- **Routed form**: along the reversed path of a flood copy heard over 1 or 2 repeaters, or along the path stored for `via`. For the first routed ACK of a flood the bridges run a claim round of 2 s (kind `24244`, fewest hops wins, 4.1), and a bridge skips its send when it sees an "ack sent" note for the same `y` in that time. The path is then stored under the new `x`, and the use restarts the 48 h lifetime of the `via` record and of its key lock.
- **Never a flood.** In every other case the entry is dropped.
- **Budget**: one live ACK per locked key and report, one per timed slot, at most 120 an hour, apart from the command budget. The hourly count is of ACKs that went on air: one skipped because the same `Pa` was heard, a claim was lost or the radio refused it costs nothing. With a command for the same report and window, the ACK goes first and the command 300 ms later (the app set `MORE`).

**"Ack sent" note.** After a bridge with a key transmitted an ACK: ephemeral kind `24244`, signed with the bridge key, `["y", x of the copy answered]` (for a timed entry its `y`, the `xa`), `["ack", "1"]` (near) or `["ack", "2"]` (routed), `["e", id of the entry]`, for a routed one `["via", x of the path record whose path it used]` (the flood copy it answered, or the record a copy 11 or a timed entry named), and for a timed one `["at", at]`. Relays do not store it. The app uses it for its latency log and the "heard but gets no answers" notice; the author of an `["ack", "2"]` note is the `p` of the following routed entries, and its `via` is their `via`. Nothing waits for it.

**"Miss" note.** When a timed entry falls due and is not sent: ephemeral kind `24244`, bridge key, `["e", id of the entry]`, `["g", g]` when it has one, `["at", at]`, `["miss", reason]` with reason `radio` (the radio is down or refused the frame until `at + 20 s`), `blocked` (a limit of 4.1), `late` (the bridge was down at `at`) or `no_path`. `no_path` (the route of the entry does not allow a send from where this bridge heard `via`) comes only from a bridge the entry names in `p`: many bridges hold a copy of an open entry, and the one that cannot reach the tag says nothing about the slot. The app shows the slot as "not sent". A timed entry counts as sent only after the radio took the frame; on a radio error the bridge retries every 2 s until `at + 20 s`.

**Command entries.** `["route", ...]` is binding:

| `route` | The bridge sends |
|---|---|
| `near` | zero-hop only, when it heard the report directly |
| `direct` | zero-hop, or along a path of 1 or 2 repeaters; never a flood |
| `flood` | the cheapest way from where it heard the tag: zero-hop for a copy heard directly, along the path for a copy heard over 1 or 2 repeaters or for a `via` with a stored path, else a flood in the report's scope. After a path send, a fallback flood (below) |
| `both` | as `flood`, and a fallback flood after a zero-hop send too. The app uses it for Lost and Track, and for any command that was not confirmed at the previous slot |

The app asks for `flood` by default and `both` for Lost and Track. For a tag the app holds as ROUTED, every command entry names the path record in `["via", x]`, the untimed ones too; a bridge that hears such a tag's report on a DIRECT route sends along that path, not zero-hop. Untimed entries of a command reach at least 10 counters ahead.

**Fallback flood.** After a zero-hop send with `both`, or any send along a path, the bridge waits 12 s for an answer: a live first hearing of a report whose `x` is a `y` of another untimed entry of the same group `g` (a later counter than the one the send was for), on any route and with any hop count. None heard: it sends the same `Pc` once more as a flood in the report's scope (for a DIRECT arrival, which has no scope: in its narrowest configured region), with channel data type `0xFF6C`. An entry without `g` gets no fallback: nothing could tell its answer, and a fallback that always fires is a flood on every send. `["fb", "0"]` on an entry turns the fallback off for it; the app puts it on every slot of a multi-grid send except the latest, never for Lost and Track (2.6). After a flood send there is no second send in that slot.

**Group done.** The same answer (a report whose `x` is a `y` of another untimed entry of the group, heard live, any route) closes the group: the bridge drops the group's remaining timed entries and publishes the done claim of 4. The 120 s guard of 4 applies only to a `y` of the same entry as `via` (a sibling copy of the same report). The "heard the same way after its own transmission" rule is gone: an answer along a path arrives DIRECT and would never match it.

**Blind LOST entry.** A timed entry with `["blind", "1"]` that names this bridge in `p`, for a command the app could not place: the bridge floods it at `at` in the country scope (or unscoped where there is none) without having heard `via`. At most 3 per tag in 24 h.

**Reply scope.** A flood a bridge sends in answer to a report uses that report's scope. The bridge finds it by testing its configured regions (`[radio] regions`, narrow first) against the report's `code[0]`, or takes the name the node resolved (Local API capabilities `rx_scope`, `scope`). A scoped report whose scope it cannot name (no region matches `code[0]`, or the node gave no code) gets a reply in the narrowest configured region, which loads the mesh least. An unscoped report gets an unscoped reply. Timed entries use the scope of `via`, kept with its hop count and path.

**Path record.** Per `x` the bridge keeps the hop count, the path and its hash size of the copy heard with the fewest hops, 48 h from the **last use**. A use for an ACK or a command restarts the 48 h of the record and of its key lock.

**Anchors** name five `y` per counter (copies 0, 1, 9, 10, 11). The app keeps them published for the next 16 counters in IDLE and 24 in TRACK and LOST, plus the two counters a reboot can land on (the next two multiples of 16 above the last counter used) and the start of the next epoch, with an expiration that covers them (up to 50 h). It publishes ACKs and commands first, then anchors, 150 ms apart, and backs off 20 s on `rate-limited:`.

## 5. DM on low battery

- **Below 25 %** (the report has `LOW_BATT`): the app sends the owner a DM over the internet, signed with the tracker's `dm_sk` (NIP-04, kind 4). Nothing extra in the mesh.
- **Below 10 %** (the app is probably not running): the tracker sends one report (even while quiet, and over the flood cap; it is a report that has to arrive, SPEC 3.2) and, once, unless that report was ACKed (0.10.0: the DM is decided at the ACK decision point, not queued with the report), sends a NIP-04 DM signed with `dm_sk` through the `#nostr` channel (`data_type 0xFF4E`, docs/nostr-mesh-bridge.md); any bridge publishes it. Since 0.6 the frame is `dm4x.full` (profile `0x12`, 165 B): full keys, so any bridge can rebuild and publish it, text at most 15 B ASCII (`batt 9%`), and the signed event has the tags `[["p", <owner hex>], ["expiration", "<created_at + 1209600>"]]`, so relays drop it after 14 days (NIP-40; nothing extra on air).
- Since 0.7.6 this happens once per crossing: both flags (report sent, DM sent) are kept in the state file, so a reboot does not repeat them, and they are armed again only by a reading of at least 20 % that is not taken on USB power. A failed ADC reading (0 mV) neither sends nor arms. Bridges publish the < 10 % report like any other, so an app or a watcher can notify from it without the DM.
- At pairing the app sends a welcome DM from `dm_sk`, so that the owner adds the contact among the known ones.

## 6. USB console

While the tracker is not locked, `status` prints `LIBRETAG KEY <K0>`. After pairing the app sends `lock`: the tracker deletes `K0`, from then on prints only `LIBRETAG ID <id>` and `locked`, and refuses settings (`ERR locked`). Unlocking for one connection:

```
> challenge
CHALLENGE <16 B hex>
> auth <hex(HMAC(usb_key, "LT2-auth" || challenge)[0:16])>
OK unlocked
```

`unpair` deletes all keys and generates a new `K0` (factory reset of pairing). It is used when the phone is lost; whoever has the tracker in hand can reset it, but cannot read the original owner's past or future reports.

The unlock lasts while the port stays open: a DTR drop (the app or terminal closes the port, the cable is pulled) ends it, and it ends after 10 minutes in any case (0.6). A locked console answers only `help`, `status` (id, lock, version, battery), `version`, `selftest`, `challenge`, `auth`, `unpair`, `buzz`. `selftest` (0.7.8, also the second line of `version`) prints `selftest nostr=ok|failed(aes256)|failed(bip340)|off gps=yes|none nmea=<sentences> [wifi=<n> scan(s) first=<n>AP empty_retried=<n>] owner=set|none uptime=<s>s`: no keys, no position, and only whether an owner is stored.

`dfu [serial|ble|uf2]` (0.7.6, unlocked) answers `dfu: rebooting to <mode>`, then saves the state, detaches USB and resets into the bootloader: serial DFU (default, GPREGRET0 `0x4E`), BLE OTA (`0xA8`) or the UF2 drive (`0x57`). Anything else gives `ERR dfu serial|ble|uf2`. In the bootloader the device has the bootloader's USB VID/PID, so the app asks for USB permission again (`docs/design/fw-0.7.6.md` 4, `docs/design/dfu.md`).

`status` (0.7.6) has one more line after `energy used since full`: `txcap floods_24h=<n> cap=200 over=yes|no low_alert=armed|reported|sent resets=<n> boot_delay=<s>s tx_floor=<mV>mV tx=ok|low_voltage`, in LOST followed by ` lost=fast|slow`.

Lines end with `\r\n`. Listings end with `END` (with a count where stated); errors start with `ERR`.

**0.10.0 console.** `area add <lat> <lon> <r_km> <scope>`, `area list` (`AREA <i> <lat> <lon> <r_km> <scope> baked|state` lines, `END <count>`), `area del <i>`, `area clear` (state-file rows only, at most 4; 2.7). `link` prints the line that `status` adds: `link near|routed <hops>|far ack <s> ago hold <h>h lvl <scope>|none floods_idle_24h=<n> anchor=<n_a> prev_slots=<n>`. `scopetest` sends one flood per level of the current position (each its own payload, 10 s apart) and prints, per level, whether a repeater was heard repeating it and its hash: `SCOPE <level> <scope>|none repeated=yes|no by=<hash>`, `END`. `ackpatience 1|2` as `SET_IDLE` offset 9. The history flags gain `near` (copy 9 sent), `routed` (copy 11 sent), `acked`, `wide` (copy 10 sent) and the level; events `link` and `lvl` on every change. The field log fields are in `docs/design/quiet-mesh.md`.

`status` (unlocked) prints the settings in two lines: `n=<n> mode=<m> interval=<min>min listen=<s>s fixto=<s>s transport=channel|stealth check=<s>s` and (0.7) `still=<after> still_hb=<h>h zone_hb=<h>h owner_hb=<h>h` (`still=0` = off). `log` adds the words `parked` and `check` for the 0.7 history bits. Settings live in the state file (v7 since 0.7; an older state migrates with the defaults).

Anchors are kept in plain form in the tracker, like zones. Only identities the device itself keeps stable work (its address, name, maker or service data, or an IRK); whatever is stable for the tracker is stable for everyone, so a static address or a name can be cloned. Never "some phone nearby": thieves carry phones too.

### 6.2 Console over Bluetooth (0.8.0)

After a boot a paired (locked) tracker listens on Bluetooth for 180 s. The owner's app connects and runs the same console as over USB: same commands, same answers, same parsers. Design and reasons: `docs/design/ble-console.md`.

**When.** At boot, if the tracker is locked, `blecon boot` is on (default), the battery is above the transmit floor (2.5) and there were at most 3 resets in a row. (Since 0.9.1 deliberate resets do not count, 2.5.) An unpaired tracker never listens. `blecon open [s]` on an unlocked console opens a window without a reboot (30 to 600 s), and so do the mesh command `BLE_CONSOLE` (section 3, 0.9.2) and the phone's console wake advert (3.2, 0.9.5, always 180 s; the boot switch and the reset count do not apply to either). After 5 failed handshakes or bad frames the window closes until the next boot. A successful handshake sets the resets in a row to 1 (the owner is there).

**Advert.** Connectable, legacy, 100 to 150 ms, from a resolvable private address (never the identity address; the IRK is random per boot and never leaves the tracker). Flags and one manufacturer specific AD, company `0xFFFF`, 14 B:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | `0x25` |
| 1 | 1 | `left`: seconds until the window closes / 2, rounded up; 255 = more than 508 s. Refreshed every 10 s, not authenticated |
| 2 | 6 | `salt`, random per window |
| 8 | 6 | `HMAC(usb_key, "LT2-bcon-adv" ‖ salt)[0:6]` |

No name, no service UUID. The app recognises its tags by computing the 6 B tag from the salt with each tag's `usb_key`.

**GATT.** Service `4C540001-7A1E-4B0C-9D2F-6C6962726574`, RX `4C540002-…` (write, write without response), TX `4C540003-…` (notify). No link encryption and no bonding. One written value or one notification is one frame; byte 0 is the type. A frame is at most `ATT_MTU − 3` B; the app asks for MTU 247, and the tracker drops a connection whose MTU is below 64 when AUTH arrives.

| Type | Direction | Body |
|---|---|---|
| `0x01` HELLO | tag → app | `ver` (`0x01`), `tag_nonce` (16 B, fresh per connection), sent when the app enables notifications |
| `0x02` AUTH | app → tag | `app_nonce` (16 B), `proof_a` (16 B) |
| `0x03` READY | tag → app | `proof_t` (16 B) |
| `0x10` DATA | both | `ct` (1 to 235 B at MTU 247), `mac` (8 B) |

```
proof_a = HMAC(usb_key, "LT2-bcon-a" ‖ tag_nonce ‖ app_nonce)[0:16]
proof_t = HMAC(usb_key, "LT2-bcon-t" ‖ tag_nonce ‖ app_nonce)[0:16]
ks      = HMAC(usb_key, "LT2-bcon-k" ‖ tag_nonce ‖ app_nonce)
kd_a    = HMAC(ks, "LT2-bcon-a2t")   # app → tag: [0:16] AES key, [16:32] MAC key
kd_t    = HMAC(ks, "LT2-bcon-t2a")   # tag → app
DATA frame c (u32 per direction, from 0):
ct  = AES-128-CTR(kd[0:16], u32le(c) ‖ 0^4 ‖ 0^8, plaintext)
mac = HMAC(kd[16:32], u32le(c) ‖ ct)[0:8]
```

The app checks `proof_t` (a decoy cannot collect its commands). A wrong proof, a bad MAC (which covers a dropped, repeated or reordered frame) or a malformed DATA frame ends the connection and counts as a failure. Writes before AUTH that are not AUTH are ignored. The plaintext is the console byte stream as on USB, with two differences: no echo, and a line buffer of its own. An empty line runs no command (the app's keepalive). Vectors: `ble_console` in `host/tests/vectors/lt2.json`.

**Limits.** AUTH within 10 s of connecting. One AUTH per connection. A session ends on disconnect, after 120 s without a frame from the app (`BLECON closing idle`), after 30 minutes (`BLECON closing max`, the window closes) or when the keys change on USB (`BLECON closing keys`). While a session is open the window stays open. After a clean disconnect the tracker advertises for what is left of the 180 s; after a session lost its link (supervision timeout) for at least 30 s more.

**Rights.** Before AUTH: nothing, not even `status`. After AUTH: an unlocked USB console minus `dfu`, `key <hex>`, `newkey`, `lock`, `unpair`, `challenge`, `auth` and `blepair`, which answer `ERR ble: use the cable`. Firmware update, first activation, re-key and reset of the pairing stay on the cable. `blepair` on USB closes the Bluetooth window first.

## 7. What a network observer sees

- hello (0.10.0): a 53 B DIRECT packet on `#libretag` with an empty path every few hours from a standing tag, answered within seconds by a 21 B DIRECT packet (the ACK) from a bridge or a phone in range, which nobody forwards;
- routed copy (0.10.0): the same report as a DIRECT packet with one or two repeater hashes in the header. A listener next to the tag sees the whole path in the first transmission and so the neighbourhood of the bridge (bridges announce themselves anyway). The routed ACK carries the same path under the public channel key. A standing tag that uses one path every time is linkable by it, as it is today by the first repeater of its floods;
- report: `GRP_DATA` flood, 51 B payload; in channel mode the hash of the `#libretag` channel (it is visible that this is LibreTag), in stealth a random one; both the content and the tag `x` change with every report;
- command: 35 B, rare, shortly after a report or at a slot; a fallback flood 12 s after a cheap send has other bytes (data type `0xFF6C`);
- BLE packets (0.6): 147 B, 1–4 right after a report or a command, only on `BLE_SCAN` and in LOST; the length tells an observer that a LibreTag sent its surroundings;
- quiet (0.6): a tracker in a home zone, near its owner or parked (0.7) sends nothing between heartbeats; checks only receive;
- command at a check (0.7): 35 B at a time that looks random, followed seconds later by a report;
- the flood path reveals the area of the transmitter (a MeshCore property); `discover` (8 B zero-hop) reveals that someone here is looking for repeaters;
- command over Bluetooth (0.7.7, 3.1): near the owner's phone, while a command waits, a non-connectable advert with manufacturer data `0xFFFF` and 21 B starting `0x22`, from the phone's rotating address; its content changes at every check of the tag, and the tag's acknowledging report follows at its next wake-up;
- console wake advert (0.9.5, 3.2): near the owner's phone, while the app waits for a tag's console, a non-connectable advert with manufacturer data `0xFFFF` and 13 B starting `0x26`; the salt changes with every session, so sessions cannot be linked without `usb_key`, and the advert names no tag;
- console over Bluetooth (0.8.0, 6.2): for up to 3 minutes after a reboot (unless `blecon boot off`) a connectable advert with manufacturer data `0xFFFF` and 14 B starting `0x25`, from a private address; salt and tag change with every window, so two windows cannot be linked without `usb_key`. It says "a LibreTag-like device just restarted here", not which one. After connecting a stranger sees the GAP name "LibreTag" and the console service; before the handshake the tracker sends only HELLO (a random nonce). An owner's session shows frame sizes and timing, not content;
- regularity: the interval has ±10 % jitter; at checks it comes from `C_e(n)`, so only the key holders can predict it.
